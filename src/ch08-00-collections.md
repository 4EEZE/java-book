# Коллекции

Массив мы уже видели. У него есть неустранимый недостаток: размер задаётся при
создании и больше не меняется.

```java
String[] names = new String[3];
```

Три места. Понадобилось четвёртое — создавайте новый массив и копируйте. А если
заранее неизвестно, сколько будет элементов — а это обычный случай, — придётся
угадывать с запасом и следить, сколько мест реально занято.

Коллекции решают это и многое другое. Их три основных вида, и различаются они
не удобством, а тем, на какой вопрос отвечают:

- **список** (`List`) — упорядоченная последовательность, элементы могут
  повторяться. «Что идёт третьим?»
- **словарь** (`Map`) — пары «ключ → значение». «Что лежит под этим ключом?»
- **множество** (`Set`) — набор без повторов. «Есть ли здесь такой элемент?»

## Список

<span class="filename">Файл: Main.java</span>

```java
import java.util.ArrayList;
import java.util.List;

void main() {
    List<String> names = new ArrayList<>();

    names.add("Аня");
    names.add("Борис");
    names.add("Вера");

    IO.println(names);
    IO.println(names.get(1));
    IO.println(names.size());
    IO.println(names.contains("Вера"));
}
```

```text
[Аня, Борис, Вера]
Борис
3
true
```

Разберём объявление `List<String> names = new ArrayList<>()`, в нём три новые
вещи.

`<String>` в угловых скобках — **обобщённый тип**: так мы сказали, что в списке
лежат строки. Компилятор проследит, чтобы туда не попало число, а при чтении
элемента не придётся ничего приводить. Подробно об этом — [глава 10](ch10-00-generics.md).

`<>` справа — пустые угловые скобки. Тип уже указан слева, повторять его незачем,
и компилятор выведет его сам.

А главное — типы слева и справа **разные**. `List` — интерфейс, тот самый, из
[главы 6](ch06-00-interfaces.md): он говорит, что список умеет, и ничего не говорит о том, как устроен.
`ArrayList` — одна из реализаций, внутри обычный массив, который при нехватке
места заменяется на больший.

> **Современный подход:** объявляйте переменную типом интерфейса, а не
> реализации: `List<String> names = new ArrayList<>()`, а не
> `ArrayList<String> names = ...`. То же касается параметров и возвращаемых
> значений: метод, принимающий `List`, примет любой список, а принимающий
> `ArrayList` — только его.
>
> Смысл в том, что реализацию потом можно поменять, не трогая остальной код. И
> в том, что читателю сообщается ровно нужное: здесь список, а какой именно —
> подробность.

## Ловушка: удалить по индексу или по значению

```java,wrong_behavior
List<Integer> numbers = new ArrayList<>(List.of(1, 2, 3));
numbers.remove(1);
IO.println(numbers);
```

```text
[1, 3]
```

Исчезла двойка, а не единица. У списка два разных метода удаления: `remove(int)`
убирает элемент **по индексу**, `remove(Object)` — **по значению**. Когда список
хранит числа, оба подходят под вызов `remove(1)`, и Java выбирает первый.

Чтобы удалить именно значение, его нужно сделать объектом явно:

```java
List<Integer> numbers = new ArrayList<>(List.of(1, 2, 3));
numbers.remove(Integer.valueOf(1));
IO.println(numbers);
```

```text
[2, 3]
```

Ловушка срабатывает только для `List<Integer>` — у списка строк неоднозначности
нет. Но встречается она достаточно часто, чтобы о ней стоило знать.

## Словарь

Словарь хранит пары «ключ → значение»:

```java
import java.util.HashMap;
import java.util.Map;

void main() {
    Map<String, Integer> ages = new HashMap<>();

    ages.put("Аня", 30);
    ages.put("Борис", 25);

    IO.println(ages.get("Аня"));
    IO.println(ages.get("Никто"));
    IO.println(ages.containsKey("Борис"));
}
```

```text
30
null
true
```

Обратите внимание на вторую строку вывода: `get` для отсутствующего ключа
возвращает `null`, а не ошибку. Это источник `NullPointerException` ровно в том
виде, который мы разбирали в [главе 4](ch04-00-references.md) — особенно если результат сразу пойдёт в
арифметику.

Поэтому чаще пользуются не `get`, а методами, которые сразу говорят, что делать
при отсутствии.

### Три метода, которые стоит знать сразу

Возьмём типичную задачу: посчитать, сколько раз встретилось каждое слово.

```java
String[] words = {"кот", "пёс", "кот"};

Map<String, Integer> count = new HashMap<>();
for (String word : words) {
    count.put(word, count.getOrDefault(word, 0) + 1);
}
IO.println(count);
```

```text
{кот=2, пёс=1}
```

`getOrDefault(ключ, значение)` возвращает значение по ключу, а если ключа нет —
то, что передали вторым аргументом. Никакого `null` и никакой проверки.

То же самое короче:

```java
Map<String, Integer> count = new HashMap<>();
for (String word : words) {
    count.merge(word, 1, Integer::sum);
}
```

```text
{кот=2, пёс=1}
```

`merge(ключ, значение, функция)` кладёт значение, если ключа не было, а если был
— применяет функцию к старому и новому. `Integer::sum` здесь — ссылка на метод
сложения; такой записи посвящена [глава 14](ch14-00-lambdas.md).

Третий метод нужен, когда значение — коллекция:

```java
Map<String, List<String>> groups = new HashMap<>();
for (String word : words) {
    groups.computeIfAbsent(word.substring(0, 1), key -> new ArrayList<>()).add(word);
}
IO.println(groups);
```

```text
{к=[кот, кот], п=[пёс]}
```

`computeIfAbsent` создаёт значение, только если ключа ещё не было, и в любом
случае возвращает его — поэтому `.add(word)` можно вызвать сразу. Без него
пришлось бы каждый раз проверять наличие ключа и создавать список вручную.

## Множество

Множество отвечает на один вопрос: есть ли такой элемент?

```java
import java.util.HashSet;
import java.util.Set;

void main() {
    Set<String> tags = new HashSet<>(List.of("кот", "пёс"));

    IO.println(tags.add("кот"));
    IO.println(tags.contains("пёс"));
    IO.println(tags.size());
}
```

```text
false
true
2
```

`add` вернул `false`: такой элемент уже был, и множество не изменилось. Размер
остался прежним — повторов в множестве не бывает.

Это же свойство — самый короткий способ убрать дубликаты: сложите список в
множество, и они исчезнут сами.

## Порядок обхода

Три реализации словаря ведут себя по-разному, и разница не в скорости:

```java
Map<String, Integer> hash = new HashMap<>();
Map<String, Integer> linked = new LinkedHashMap<>();
Map<String, Integer> tree = new TreeMap<>();
// в каждый кладём яблоко, банан, апельсин — в этом порядке
```

```text
HashMap:       [банан, яблоко, апельсин]
LinkedHashMap: [яблоко, банан, апельсин]
TreeMap:       [апельсин, банан, яблоко]
```

`HashMap` не обещает **никакого** порядка. Полученный здесь — не случайный и не
обратный, он просто следствие внутреннего устройства, и полагаться на него
нельзя: изменится набор ключей — изменится и порядок.

`LinkedHashMap` хранит порядок добавления. `TreeMap` держит ключи
отсортированными.

Отсюда практическое правило: если порядок важен — скажите об этом типом, а не
надейтесь. У множеств есть ровно такая же тройка: `HashSet`, `LinkedHashSet`,
`TreeSet`.

> **Под капотом:** имя `HashMap` описывает устройство. Внутри массив ячеек;
> чтобы найти место ключа, вызывается его `hashCode()`, и число приводится к
> номеру ячейки. Поэтому поиск не зависит от размера словаря: он не перебирает
> ключи, а сразу вычисляет, где смотреть.
>
> Отсюда же понятно, почему у `ArrayList` быстро `get(i)` — это обращение к
> ячейке массива — и медленно удаление из начала: все последующие элементы
> нужно сдвинуть. И почему `TreeMap` медленнее `HashMap`: он не вычисляет
> позицию, а спускается по дереву, сравнивая ключи.

## Ловушка: изменение во время обхода

Вот это стоит разобрать внимательно, потому что ошибка выглядит безобидно:

```java,throws
List<String> items = new ArrayList<>(List.of("а", "б", "в"));

for (String s : items) {
    if (s.equals("а")) {
        items.remove(s);
    }
}
```

```text
Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1104)
```

Коллекцию нельзя изменять, пока по ней идёт обход: обходчик считает элементы и
сбивается, когда список меняется под ним. Java это замечает и прерывает работу.

А теперь то же самое, но удаляем не первый элемент, а второй:

```java,wrong_behavior
List<String> items = new ArrayList<>(List.of("а", "б", "в"));

for (String s : items) {
    if (s.equals("б")) {
        items.remove(s);
    }
}

IO.println(items);
```

```text
[а, в]
```

Исключения нет. Программа отработала и даже выдала правдоподобный результат.

Разница в том, что после удаления второго элемента из трёх длина стала равна
двум, а обходчик как раз стоял на позиции два — и решил, что элементы
закончились. Проверка, которая обнаружила бы изменение, находится внутри
перехода к следующему элементу, а перехода не случилось.

Это худший вид ошибки: код с настоящим дефектом на одних данных падает, а на
других тихо работает. Тесты на трёх элементах проходят, а в бою всё
разваливается.

Правильный способ удалить по условию — `removeIf`:

```java
List<String> items = new ArrayList<>(List.of("а", "б", "в"));
items.removeIf(s -> s.equals("а"));
IO.println(items);
```

```text
[б, в]
```

`s -> s.equals("а")` — лямбда, то есть функция без имени; ей посвящена глава 14.
Пока достаточно читать это как «условие, по которому удалять».

## Ловушка: изменяемый ключ

Вторая ловушка тоньше, и она объясняет, почему предыдущая глава так настаивала
на неизменяемости.

Возьмём ключ с изменяемым полем. Методы `equals` и `hashCode` написаны
правильно — по значению поля; чем они занимаются, подробно разберём в [главе 11](ch11-00-object-contracts.md):

<span class="filename">Файл: Key.java</span>

```java
public class Key {
    public int value;

    public Key(int value) {
        this.value = value;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Key other && other.value == value;
    }

    @Override
    public int hashCode() {
        return Integer.hashCode(value);
    }

    @Override
    public String toString() {
        return "Key(" + value + ")";
    }
}
```

```java,wrong_behavior
Key k = new Key(1);
Set<Key> set = new HashSet<>();
set.add(k);

IO.println("до:    contains=" + set.contains(k) + " " + set);
k.value = 2;
IO.println("после: contains=" + set.contains(k) + " " + set);
```

```text
до:    contains=true [Key(1)]
после: contains=false [Key(2)]
```

Прочитайте вторую строку ещё раз. Множество содержит `Key(2)`, мы спрашиваем,
содержит ли оно `k`, а `k` — это и есть `Key(2)`. Ответ: нет.

Причина в устройстве, которое мы только что разобрали. При добавлении множество
вычислило `hashCode()` и положило объект в соответствующую ячейку. Изменив поле,
мы изменили и `hashCode()` — а объект остался лежать в старой ячейке. Теперь
поиск идёт в новую ячейку и ничего там не находит.

Объект потерян: он в множестве, но недостижим. Такую ошибку не покажет ни
компилятор, ни тест, который не меняет ключи.

Отсюда правило: **ключи словарей и элементы множеств должны быть
неизменяемыми**. Лучший кандидат — запись из [главы 7](ch07-00-records-and-patterns.md) или строка. Если ключ
изменяемый, его нельзя менять, пока он лежит в коллекции.

## Неизменяемые коллекции

Для наборов, которые не меняются, есть короткая запись:

```java
List<String> days = List.of("пн", "вт", "ср");
Map<String, Integer> limits = Map.of("малый", 10, "большой", 100);
Set<String> colors = Set.of("красный", "синий");
```

Такие коллекции нельзя изменить — `add` бросит `UnsupportedOperationException`,
как мы видели в главе 4. Для констант это ровно то, что нужно.

Обратите внимание на приём, который встречался в примерах выше:
`new ArrayList<>(List.of("а", "б", "в"))` — создать изменяемый список с
начальным содержимым. Просто `List.of(...)` не подойдёт: изменять его нельзя.

## Что выбирать

| Задача | Берите |
|---|---|
| Последовательность, обращение по индексу | `ArrayList` |
| Частые вставки и удаления в начале | `ArrayDeque` |
| Пары «ключ → значение» | `HashMap` |
| То же, с сохранением порядка добавления | `LinkedHashMap` |
| То же, с сортировкой по ключу | `TreeMap` |
| Уникальные элементы | `HashSet` |
| Очередь, стек | `ArrayDeque` |
| Константа | `List.of`, `Map.of`, `Set.of` |

`ArrayList` и `HashMap` покрывают подавляющее большинство случаев. Начинайте с
них и меняйте, когда появится причина.

Отдельно стоит сказать про `LinkedList`: он есть в стандартной библиотеке, его
часто упоминают в учебниках как альтернативу `ArrayList`, и на практике он почти
никогда не нужен. Если требуется быстрая вставка с обоих концов, берите
`ArrayDeque` — он и для очереди, и для стека.

И про класс `Stack`: им пользоваться не стоит по причине, которую мы разбирали в
главе 6, — он наследует `Vector` и потому умеет лишнее. Для стека тоже
`ArrayDeque`.

## Итоги

Вы умеете пользоваться списком, словарём и множеством и
понимаете, на какой вопрос отвечает каждый. Знаете, почему переменную
объявляют типом интерфейса. Умеете считать и группировать через
`getOrDefault`, `merge` и `computeIfAbsent`. Знаете, что `HashMap` не обещает
порядка, а `LinkedHashMap` и `TreeMap` обещают разный. И знаете три ловушки:
`remove` по индексу вместо значения, изменение коллекции во время обхода — с
тем неприятным свойством, что иногда оно проходит молча, — и изменяемый ключ,
который теряет объект внутри множества.

Мы дважды за главу столкнулись с тем, что что-то идёт не так во время работы
программы: `ConcurrentModificationException`,
`UnsupportedOperationException`. Пора разобраться с исключениями как следует —
это следующая глава.
