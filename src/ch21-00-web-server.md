# Проект: многопоточный веб-сервер

Соберём всё вместе. Напишем настоящий HTTP-сервер — без библиотек и каркасов,
на голых сокетах, — который отвечает нескольким клиентам одновременно.

Задача выбрана не случайно: она задействует почти всё из книги. Записи и
запечатанные варианты из главы 7, коллекции из главы 8, исключения из главы 9,
`try` с ресурсами из главы 4, кодировки из главы 16, атомарный счётчик из главы
18 и виртуальные потоки из главы 19.

## Что такое сервер на самом деле

HTTP устроен проще, чем кажется. Клиент открывает соединение и присылает текст:

```text
GET /count HTTP/1.1
Host: localhost:8081

```

Первая строка — метод, путь и версия. Дальше заголовки, по одному на строку.
Пустая строка означает конец.

Сервер отвечает тоже текстом:

```text
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 13

посещений: 1
```

Всё. Никакой магии: чтение строк и запись строк в сокет.

Одна деталь, о которой спотыкаются: строки в HTTP разделяются **двумя**
символами — возвратом каретки и переводом строки, `\r\n`. Не одним.

## Сокет

**Сокет** — конец соединения. Серверный сокет слушает порт и ждёт, пока кто-то
подключится:

```java
try (ServerSocket server = new ServerSocket(8081)) {
    while (true) {
        Socket socket = server.accept();
        handle(socket);
    }
}
```

`accept()` **блокирует** выполнение, пока клиент не подключится, и возвращает
сокет для разговора именно с ним.

Здесь и возникает главная задача. Пока `handle` обслуживает одного клиента,
цикл не дойдёт до следующего `accept()`, и все остальные будут ждать. Один
медленный клиент заблокирует всех.

## Поток на клиента

Решение очевидное: обслуживать каждого клиента отдельно.

```java
while (true) {
    Socket socket = server.accept();
    Thread.ofVirtual().start(() -> handle(socket));
}
```

Виртуальный поток из главы 19 — ровно то, что нужно. Сервер почти всё время
ждёт: ждёт подключения, ждёт запроса, ждёт, пока клиент прочитает ответ.
Обычными потоками пришлось бы заводить пул и ограничивать число клиентов;
виртуальных можно создавать по одному на соединение и не считать их.

## Разбор запроса

```java
record Request(String method, String path) {}

Request parse(BufferedReader in) throws IOException {
    String line = in.readLine();
    if (line == null || line.isBlank()) {
        return null;
    }

    String[] parts = line.split(" ");
    if (parts.length < 2) {
        return null;
    }

    while (true) {
        String header = in.readLine();
        if (header == null || header.isEmpty()) {
            break;
        }
    }

    return new Request(parts[0], parts[1]);
}
```

Заголовки мы вычитываем и выбрасываем — но вычитать их **обязательно**. Если
оставить их в буфере, следующее чтение получит мусор.

`null` из `readLine()` означает, что клиент закрыл соединение, — знакомый по
главе 2 случай конца ввода. Браузеры регулярно открывают соединение и сразу
закрывают, так что случай не теоретический.

Обратите внимание, что `parse` возвращает `null` при негодном запросе. Это то
самое, чего мы советовали избегать в главе 4, — и здесь допустимо ровно потому,
что метод приватный, а единственный вызывающий проверку делает сразу.
В публичном интерфейсе стоило бы вернуть `Optional` из главы 15.

## Маршрутизация

```java
record Response(int code, String reason, String body) {
    static Response ok(String body) {
        return new Response(200, "OK", body);
    }

    static Response notFound() {
        return new Response(404, "Not Found", "не найдено\n");
    }
}
```

```java
static final AtomicLong visits = new AtomicLong();

Response route(Request request) {
    if (!request.method().equals("GET")) {
        return new Response(405, "Method Not Allowed", "только GET\n");
    }

    return switch (request.path()) {
        case "/" -> Response.ok("привет\n");
        case "/count" -> Response.ok("посещений: " + visits.incrementAndGet() + "\n");
        default -> Response.notFound();
    };
}
```

Вот здесь внимательно. `visits` — общее состояние, к которому обращаются
**все** потоки сразу. Если бы это было обычное `long` поле с `visits++`,
счётчик терял бы посещения ровно так, как мы видели в главе 18.

`AtomicLong` делает увеличение неделимым. Проверим это позже нагрузкой.

Статические методы `ok` и `notFound` внутри записи — распространённый приём:
конструктор остаётся один, а называть частые случаи удобно.

## Ответ

```java
void write(BufferedWriter out, Response response) throws IOException {
    byte[] body = response.body().getBytes(StandardCharsets.UTF_8);

    out.write("HTTP/1.1 " + response.code() + " " + response.reason() + "\r\n");
    out.write("Content-Type: text/plain; charset=utf-8\r\n");
    out.write("Content-Length: " + body.length + "\r\n");
    out.write("Connection: close\r\n\r\n");
    out.write(response.body());
    out.flush();
}
```

Три вещи, каждая из которых источник ошибок.

**`Content-Length` считается в байтах, а не в символах.** Для кириллицы это
разные числа: в UTF-8 русская буква занимает два байта. Ошибётесь — клиент
будет ждать недостающие байты или обрежет ответ. Поэтому длину берём у
`getBytes`, а не у `length()`.

**Кодировка указывается дважды:** в заголовке — чтобы клиент знал, как читать, и
при создании `OutputStreamWriter` — чтобы мы писали именно так. Это прямое
следствие главы 16: кодировка — не то, о чём стоит догадываться.

**`flush()` обязателен.** Буферизованный писатель накапливает данные, и без
явного сброса ответ может остаться в буфере, а клиент — ждать вечно.

## Обработка соединения

```java
void handle(Socket socket) {
    try (socket;
         var in = new BufferedReader(
             new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8));
         var out = new BufferedWriter(
             new OutputStreamWriter(socket.getOutputStream(), StandardCharsets.UTF_8))) {

        Request request = parse(in);
        if (request == null) {
            return;
        }

        write(out, route(request));
    } catch (IOException e) {
        IO.println("сбой соединения: " + e.getMessage());
    }
}
```

`try` с ресурсами из главы 4 закрывает всё три — и, что важно, **в обратном
порядке**: сначала писатель, потом читатель, потом сокет. Если бы сокет закрылся
первым, сброс буфера писателя провалился бы.

Запись `try (socket; ...)` — сокращённая форма: если переменная уже
существует и реализует `AutoCloseable`, её можно просто перечислить.

Перехват `IOException` здесь уместен по правилу главы 9: разорванное соединение
— штатное событие, а не ошибка программы. Один упавший клиент не должен ронять
сервер, поэтому исключение ловится в пределах одного соединения.

## Проверяем

```console
$ java Server.java
слушаю порт 8081
```

```console
$ curl -s http://localhost:8081/
привет

$ curl -s http://localhost:8081/count
посещений: 1

$ curl -s -i http://localhost:8081/нет | head -1
HTTP/1.1 404 Not Found

$ curl -s -i -X POST http://localhost:8081/ | head -1
HTTP/1.1 405 Method Not Allowed
```

Теперь главное — нагрузка. Двести запросов по пятьдесят одновременно:

```console
$ seq 1 200 | xargs -P 50 -I{} curl -s http://localhost:8081/count > /dev/null
$ curl -s http://localhost:8081/count
посещений: 204
```

Счётчик сошёлся: три запроса до этого, двести параллельных и один проверочный.
Ни одно посещение не потеряно.

Замените `AtomicLong` на обычное `long` поле с `visits++`, повторите — и
получите число меньше. Это гонка из главы 18, вживую и на настоящей нагрузке.

## Чего здесь нет

Честный список того, что отделяет нашу программу от настоящего сервера.

**Тайм-аутов.** Клиент, открывший соединение и молчащий, займёт поток навсегда.
Лечится `socket.setSoTimeout(...)`.

**Ограничений.** Запрос в гигабайт заголовков съест память. Настоящий сервер
ограничивает длину строки, число заголовков и размер тела.

**Тела запроса.** Мы читаем только первую строку и заголовки; для POST нужно
прочитать ещё `Content-Length` байтов.

**Постоянных соединений.** Мы всегда отвечаем `Connection: close`. HTTP/1.1
позволяет переиспользовать соединение, и это заметно быстрее.

**Безопасности.** Ни TLS, ни разбора путей с проверкой на выход за пределы
каталога.

> **Современный подход:** писать HTTP-сервер вручную стоит ровно один раз — чтобы
> увидеть, что внутри нет никакой магии. В работе берут готовое.
>
> В самой Java есть `com.sun.net.httpserver.HttpServer` — простой встроенный
> сервер, годный для служебных нужд и небольших сервисов. Для настоящих
> приложений используют каркасы: Spring Boot, Quarkus, Micronaut, Javalin. Они
> решают всё из списка выше, и решают лучше, чем получится у вас.
>
> Но час, потраченный на этот проект, окупается: увидев, что запрос — это просто
> текст в сокете, вы перестанете относиться к каркасу как к чёрному ящику.

> **Получилось:** вы написали работающий многопоточный HTTP-сервер с нуля. Он
> принимает соединения, разбирает запросы, маршрутизирует их, считает общий
> счётчик без потерь под параллельной нагрузкой и корректно закрывает ресурсы.
> И вы знаете, чего в нём не хватает до настоящего.
