## Копирование, `null` и мутации

Мы выяснили, что присваивание ссылочной переменной копирует ссылку, а не объект.
Теперь посмотрим, во что это обходится на практике.

## Псевдонимы

Когда на один объект указывают две переменные, их называют **псевдонимами**.
Само по себе это не плохо — плохо, когда про это забывают:

```java,wrong_behavior
import java.util.ArrayList;
import java.util.List;

void main() {
    List<String> original = new ArrayList<>();
    original.add("первый");

    List<String> backup = original;
    original.add("второй");

    IO.println("Резервная копия: " + backup);
}
```

```text
Резервная копия: [первый, второй]
```

Переменная названа `backup`, но никакой копии не сделано: `backup` и `original`
— два имени одного списка. «Резервная копия» изменяется вместе с оригиналом.

Компилируется, не падает, делает не то. Чтобы получить настоящую копию, её надо
создать явно:

```java
import java.util.ArrayList;
import java.util.List;

void main() {
    List<String> original = new ArrayList<>();
    original.add("первый");

    List<String> backup = new ArrayList<>(original);
    original.add("второй");

    IO.println("Резервная копия: " + backup);
}
```

```text
Резервная копия: [первый]
```

`new ArrayList<>(original)` создаёт новый список с теми же элементами.

Оговорка, о которой стоит знать сразу: скопированы **ссылки** на элементы, а не
сами элементы. Списки теперь разные, но объекты внутри — общие. Такое
копирование называют **поверхностным**; если элементы изменяемы, их тоже
придётся копировать, и тогда речь идёт о **глубоком** копировании. Для строк
разницы нет — они неизменяемы.

## Чем `final` не является

В третьей главе мы обещали вернуться к тому, что `final` фиксирует имя, а не
содержимое. Вот наглядно:

```java
import java.util.ArrayList;

void main() {
    final var items = new ArrayList<String>();
    items.add("первый");
    items.add("второй");
    IO.println(items);
}
```

```text
[первый, второй]
```

Переменная помечена `final`, список меняется — и компилятор не возражает.
Запрещено ровно одно: присвоить `items` другой список.

```java,does_not_compile
import java.util.ArrayList;

void main() {
    final var items = new ArrayList<String>();
    items = new ArrayList<>();
}
```

```text
error: cannot assign a value to final variable items
    items = new ArrayList<>();
    ^
```

Если нужна именно неизменяемость содержимого, её обеспечивает не `final`, а сам
объект:

```java,throws
import java.util.List;

void main() {
    List<String> items = List.of("первый", "второй");
    items.add("третий");
}
```

```text
Exception in thread "main" java.lang.UnsupportedOperationException
	at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:145)
```

`List.of` возвращает неизменяемый список: попытка что-то добавить даёт
исключение. Обратите внимание — исключение во время работы, а не ошибка
компиляции. Тип `List` один и тот же, и по нему компилятор не различает
изменяемые и неизменяемые реализации.

> **Современный подход:** делайте объекты неизменяемыми по умолчанию, а
> изменяемость добавляйте, когда она действительно нужна. Неизменяемый объект
> нельзя испортить из другого места программы, его безопасно передавать куда
> угодно и использовать из нескольких потоков без блокировок — а это разом
> снимает целые категории ошибок из глав 4 и 18.
>
> Практически это значит: `List.of`, `Map.of`, `Set.of` для готовых наборов;
> `final` на полях; записи (`record`) вместо классов с изменяемыми полями — им
> посвящена [глава 7](ch07-00-records-and-patterns.md). Изменяемый `ArrayList` стоит заводить тогда, когда список
> действительно наполняется по ходу дела.

## `null`

`null` — значение, которое можно присвоить любой ссылочной переменной. Означает
оно «ссылка никуда не указывает».

```java
void main() {
    String name = null;
    IO.println(name);
    IO.println(name == null);
}
```

```text
null
true
```

Печатать `null` можно. А вот вызвать у него метод — нельзя:

```java,throws
void main() {
    String name = null;
    IO.println(name.length());
}
```

```text
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because "<local1>" is null
```

Это `NullPointerException`, сокращённо NPE — самое известное исключение Java.
Возникает оно всегда по одной причине: обращение к члену объекта там, где
объекта нет.

Современная JVM старается объяснить, что именно оказалось пустым, и в сообщении
две части: какой метод не удалось вызвать (`Cannot invoke "String.length()"`) и
почему (`because ... is null`).

Вторая часть иногда загадочна. `<local1>` — это наша переменная `name`, только
без имени: имена локальных переменных по умолчанию **не попадают** в
скомпилированный класс. Скомпилируйте с флагом `-g`, и они появятся:

```console
$ javac -g -d out Example.java
$ java -cp out Example
```

```text
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because "name" is null
```

А вот там, где источник виден и без отладочной информации, сообщение полезно
сразу — и особенно в длинных цепочках вызовов:

```java,throws
void main() {
    IO.println(findName().length());
}

String findName() {
    return null;
}
```

```text
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because the return value of "Example.findName()" is null
```

`the return value of ...` называет виновника точно. Когда в строке пять вызовов
подряд, это экономит много времени: раньше сообщение состояло из одного слова
`NullPointerException`, и выяснять, какое звено оказалось пустым, приходилось
самостоятельно.

Кстати, обратите внимание на сам пример: массив из двух элементов создан, но
элементы в нём — `null`. Массив ссылочного типа заполняется `null`, массив
чисел — нулями, массив `boolean` — значениями `false`. Своего рода исключение
из правила об обязательной инициализации: для элементов массива значение по
умолчанию есть.

## Что с этим делать

Полностью избавиться от `null` в Java нельзя — он встроен в язык. Но свести
встречи с ним к минимуму можно, и подходов несколько.

**Не возвращайте `null` из своих методов.** Пустой список, пустая строка или
`Optional` почти всегда лучше. Метод, который иногда возвращает `null`,
заставляет проверять результат каждого вызова — а забыть проверку легко.

**Проверяйте входные данные на границе.** Для этого есть готовый метод:

```java,throws
import java.util.Objects;

void main() {
    greet(null);
}

void greet(String name) {
    Objects.requireNonNull(name, "имя не задано");
    IO.println("Привет, " + name);
}
```

```text
Exception in thread "main" java.lang.NullPointerException: имя не задано
```

Смысл в том, чтобы упасть сразу и с внятным сообщением, а не через двадцать
строк с невнятным. Ошибка обнаруживается там, где `null` появился, а не там,
где на него в конце концов наступили.

**Используйте `Optional` для «значения может не быть».** Это тип, который явно
говорит: результата может не оказаться, — и заставляет с этим считаться. Ему
посвящена [глава 15](ch15-00-streams.md).

Автор самой идеи `null`, Тони Хоар, впоследствии называл её своей ошибкой на
миллиард долларов. Мы не в том положении, чтобы её отменить, но в том, чтобы не
усугублять.
