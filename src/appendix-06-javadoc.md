# Приложение F — Как читать документацию

## Javadoc

Документация стандартной библиотеки Java собрана из комментариев в её же
исходниках. Формат называется **Javadoc**, и знать его нужно с двух сторон: чтобы
читать чужую документацию и чтобы писать свою.

Комментарий Javadoc начинается с `/**` — двух звёздочек, в отличие от обычного
`/*`:

```java
/**
 * Возвращает самые частые слова текста.
 *
 * <p>Слова сравниваются без учёта регистра. При равной частоте порядок
 * определяется по алфавиту, поэтому результат устойчив между запусками.
 *
 * @param text  текст для разбора; не может быть {@code null}
 * @param limit сколько слов вернуть; если их меньше, вернётся сколько есть
 * @return список пар «слово и счётчик», от частых к редким
 * @throws IllegalArgumentException если {@code limit} отрицателен
 */
public static List<Entry> topWords(String text, int limit) { ... }
```

Первое предложение — самое важное: именно оно попадает в сводные таблицы и
показывается в подсказке IDE. Пишите его так, чтобы оно было понятно в отрыве от
остального.

Основные пометки:

| Пометка | Для чего |
|---|---|
| `@param` | параметр и что он означает |
| `@return` | что возвращается |
| `@throws` | когда бросается исключение |
| `@see` | ссылка на связанное |
| `@since` | с какой версии появилось |
| `@deprecated` | почему устарело и чем заменить |
| `{@code ...}` | текст как код |
| `{@link ...}` | ссылка на класс или метод |

Собирается документация командой `javadoc` из приложения D.

## Что писать, а что нет

> **Современный подход:** документировать стоит **договор**, а не устройство.
> Договор — это то, на что вызывающий может рассчитывать: что принимается, что
> возвращается, когда бросается исключение, что бывает при `null`, изменяется ли
> переданный объект, безопасен ли метод в нескольких потоках.
>
> Устройство документировать не нужно: оно меняется, комментарий устаревает, а
> вводит в заблуждение он дольше, чем помогал.
>
> Комментарии вида «геттер имени» над `getName()` — чистый шум. Не пишите их:
> они не добавляют информации, но заставляют читателя тратить внимание.
>
> Отдельно важно: комментарий, который **противоречит** коду, хуже отсутствия
> комментария. Меняя метод, поменяйте и его описание.

Что документировать обязательно, даже если кажется очевидным:

- **Поведение при `null`** — принимает ли метод `null` и что тогда делает.
- **Изменяется ли аргумент** — метод, меняющий переданную коллекцию, обязан
  сказать об этом; иначе получится история из главы 8 с псевдонимами.
- **Границы и краевые случаи** — что при пустом вводе, нуле, отрицательном
  числе.
- **Потокобезопасность** — если объект предполагается использовать из нескольких
  потоков, это часть договора.

## Как читать чужую документацию

Официальная документация библиотеки Java лежит на сайте Oracle, отдельно для
каждой версии. Ищется проще всего запросом вида «java 25 Optional javadoc».

Читая описание незнакомого класса, обращайте внимание на три вещи.

**Заголовок класса.** В нём почти всегда сказано главное: неизменяем ли объект,
безопасен ли в нескольких потоках, для чего задуман. У `String` там сказано про
неизменяемость, у `ArrayList` — что он **не** синхронизирован.

**`@throws` у метода.** Часто именно здесь обнаруживается, что метод бросает
`UnsupportedOperationException` или не принимает `null`.

**`@since`.** Если метод появился в версии новее вашей, его у вас нет — частая
причина недоумения при чтении статей.

## Где искать ответы

**Документация библиотеки** — первое место. Она подробнее и точнее любых
пересказов.

**Исходники стандартной библиотеки** доступны прямо из IDE: нажатие на имя класса
открывает его код. Читать их полезнее, чем кажется, — многое написано понятно и с
объяснениями.

**JEP** — предложения по развитию платформы, о которых говорилось в приложении E.
Лучший источник, чтобы понять **зачем** появилась возможность.

**Спецификация языка** (JLS) — окончательный ответ на вопрос «как это работает
на самом деле». Читается тяжело, но когда спор зашёл в тупик, точку ставит она.

О чём стоит помнить, читая ответы на форумах: Java сильно изменилась за последние
годы. Ответ 2015 года может быть верным, но описывать способ, который сегодня
делается втрое короче. Смотрите на дату.
