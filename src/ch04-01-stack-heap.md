## Стек, куча и ссылки

Начнём с вопроса, который выглядит наивным: что лежит в переменной?

Ответ зависит от типа, и вариантов ровно два.

## Примитивы лежат в переменной

```java
void main() {
    int a = 5;
    int b = a;
    b = 99;
    IO.println(a);
}
```

```text
5
```

`int` — примитивный тип. Переменная `a` содержит само число. Присваивание
`b = a` скопировало значение, и дальше это две независимые ячейки.

Схематически:

```text
a: [ 5  ]
b: [ 99 ]
```

Всё предсказуемо. Именно так ведут себя все восемь примитивных типов: `int`,
`long`, `double`, `float`, `short`, `byte`, `char`, `boolean`.

## Объекты лежат в куче

```java
void main() {
    int[] first = {1, 2, 3};
    int[] second = first;
    second[0] = 99;
    IO.println(first[0]);
}
```

```text
99
```

А вот это уже удивляет. Мы изменили `second`, а изменился `first`.

Дело в том, что массив — не примитив. Сам массив лежит в **куче** — общей
области памяти для объектов. А переменная `first` содержит не массив, а
**ссылку** на него: по сути адрес, по которому массив можно найти.

```text
            куча
first: [•]───────▶ [99][2][3]
                     ▲
second: [•]──────────┘
```

Присваивание `second = first` скопировало **ссылку**, а не массив. Теперь две
переменные указывают на один и тот же объект, и изменение через любую из них
видно через обе.

Убедиться можно прямым сравнением:

```java
void main() {
    int[] first = {1, 2, 3};
    int[] second = first;
    IO.println(first == second);
}
```

```text
true
```

`==` для ссылочных типов отвечает на вопрос «это один и тот же объект?», а не
«одинаковое ли содержимое?». Здесь объект действительно один.

Сравните с двумя разными массивами одинакового содержимого:

```java
void main() {
    int[] first = {1, 2, 3};
    int[] second = {1, 2, 3};
    IO.println(first == second);
}
```

```text
false
```

Содержимое совпадает, объекты разные — и `==` говорит `false`. Это не ошибка и
не странность: он и не обещал сравнивать содержимое.

Сравнить именно содержимое массивов умеет `java.util.Arrays.equals`:

```java
import java.util.Arrays;

void main() {
    int[] first = {1, 2, 3};
    int[] second = {1, 2, 3};
    IO.println(Arrays.equals(first, second));
}
```

```text
true
```

## Стек и куча

Раз уж мы упомянули кучу, разграничим её со стеком — эти два слова будут
встречаться постоянно.

**Стек** — память вызовов методов. Когда метод вызывается, для него выделяется
кадр: там лежат его параметры и локальные переменные. Когда метод завершается,
кадр уничтожается целиком, мгновенно и бесплатно. Стек невелик (по умолчанию
порядка мегабайта) и строго упорядочен: последним вошёл — первым вышел.

**Куча** — память объектов. Всё, что создано через `new`, живёт там. Куча
большая, неупорядоченная, и освобождается не по выходу из метода, а сборщиком
мусора, когда объект больше никому не нужен.

Локальная переменная всегда живёт в стеке. Но если её тип ссылочный, в стеке
лежит только ссылка, а сам объект — в куче:

```java
void main() {
    int count = 5;
    int[] values = {1, 2, 3};
}
```

```text
   стек (кадр main)          куча
   ┌──────────────┐
   │ count: 5     │
   │ values: [•]──┼────────▶ [1][2][3]
   └──────────────┘
```

Отсюда следует практический вывод, который пригодится в [главе 18](ch18-00-concurrency.md): у каждого
потока свой стек, а куча одна на всех. Поэтому локальные переменные потокам
делить не приходится, а объекты — приходится.

> **Под капотом:** деление «примитивы в стеке, объекты в куче» — хорошая рабочая
> модель, но не буква спецификации. Спецификация JVM не обязывает размещать
> объекты именно в куче, и современные виртуальные машины этим пользуются: если
> анализ показывает, что объект не покидает метод, JVM может вовсе не создавать
> его, разложив поля по регистрам. Называется это escape analysis, и работает
> оно молча.
>
> Знать об этом полезно, чтобы не проектировать код вокруг мифа «создание
> объекта — всегда дорого». Полагаться — не стоит: оптимизация применяется по
> усмотрению JVM и без гарантий.

## `new` и литералы

Объект в куче создаётся через `new`:

```java
void main() {
    Object thing = new Object();
    IO.println(thing != null);
}
```

```text
true
```

Некоторые объекты можно создать и без `new` — для них у языка есть литералы:
массив через `{1, 2, 3}`, строка через `"текст"`. Объект всё равно создаётся в
куче, просто синтаксис короче.

Со строками, впрочем, всё интереснее, и это стоит отдельного разбора.

## Строки и пул

```java
void main() {
    String a = "привет";
    String b = "привет";
    IO.println(a == b);
}
```

```text
true
```

Два литерала — а объект один. Виртуальная машина держит **пул строк**: все
одинаковые строковые литералы в программе указывают на один экземпляр. Раз
строки неизменяемы, делить их безопасно — испортить общий объект невозможно.

Но стоит создать строку явно:

```java
void main() {
    String a = "привет";
    String c = new String("привет");
    IO.println(a == c);
    IO.println(a.equals(c));
}
```

```text
false
true
```

`new String(...)` честно создаёт новый объект в куче, мимо пула. Содержимое то
же, объект другой — `==` говорит `false`, `equals` говорит `true`.

Оба случая рядом:

```text
   String a = "привет";          String c = new String("привет");
   String b = "привет";

   стек          пул строк       стек              куча
   a: [•]──┐                     a: [•]──▶ "привет"   (в пуле)
           ├──▶ "привет"
   b: [•]──┘                     c: [•]──▶ "привет"   (отдельный объект)

   a == b  →  true               a == c  →  false
                                 a.equals(c) → true
```

Слева одна стрелка ведёт из двух переменных в один объект — потому `==` и даёт
`true`. Справа объекта два, и `==` честно отвечает, что это разные объекты,
хотя содержимое у них совпадает.

Вот почему в Java строки **никогда** не сравнивают через `==`. Сравнение может
случайно сработать на литералах и сломаться на строке, прочитанной из файла или
собранной из частей. Такая ошибка проходит тесты и падает в бою.

```java
void main() {
    String expected = "да";
    String fromInput = "д" + readSuffix();
    IO.println(expected == fromInput);
    IO.println(expected.equals(fromInput));
}

String readSuffix() {
    return "а";
}
```

```text
false
true
```

Строка, собранная во время работы программы, в пул не попадает — и `==`
ожидаемо даёт `false`, хотя содержимое совпадает.
