# Пакеты, модули и зависимости

Глубокое дерево каталогов из главы 1 мы объяснили одной фразой: путь к файлу
обязан совпадать с именем пакета. Пора разобраться, что такое пакет и зачем он
нужен помимо порядка в каталогах.

## Пакет

**Пакет** — пространство имён. Он решает задачу, которая возникает в любом
проекте: два разных класса хотят называться одинаково.

Класс `Book` в вашей программе и класс `Book` в подключённой библиотеке —
обычное дело. Полное имя класса включает пакет, поэтому конфликта нет:
`ru.example.model.Book` и `com.library.Book` — разные типы.

Объявляется пакет первой строкой файла:

<span class="filename">Файл: ru/example/model/Book.java</span>

```java
package ru.example.model;

public record Book(String title, int year) {}
```

Путь к файлу обязан повторять имя пакета: класс из `ru.example.model` лежит в
каталоге `ru/example/model`. Это требование компилятора, а не соглашение.

## Импорт

Чтобы не писать полное имя каждый раз, класс импортируют:

```java
package ru.example.app;

import ru.example.model.Book;

public class Main {
    public static void main(String[] args) {
        Book book = new Book("Идиот", 1869);
    }
}
```

Импорт не подключает и не загружает ничего — он лишь сообщает компилятору, что в
этом файле означает короткое имя. Из того же пакета импортировать не нужно, как и
из `java.lang`: `String`, `Integer`, `IO` доступны всегда.

Про `import static` мы говорили в главе 12: он импортирует не класс, а
статический член, и злоупотреблять им не стоит — читатель теряет из виду, откуда
взялось имя.

Про импорт всего пакета через `import ru.example.model.*;` скажем коротко: так
делать не принято. Явные импорты показывают зависимости файла списком, и IDE
расставляет их сама.

## Четыре уровня доступа

В главе 5 мы отложили этот разговор. Вот полная картина:

| Модификатор | Кто видит |
|---|---|
| `private` | только свой класс |
| *(ничего не написано)* | свой класс и весь свой пакет |
| `protected` | то же, плюс наследники из других пакетов |
| `public` | все |

Второй уровень — **пакетно-приватный** — не имеет ключевого слова: он получается,
когда модификатор не написан вовсе. Именно так объявлено большинство методов в
примерах первых глав.

Посмотрим на него в деле:

```java
package ru.example.model;

public record Book(String title, int year) {
    String internalNote() { return "видно только в пакете"; }
}
```

Сосед по пакету обращается свободно:

```java
package ru.example.model;

public class Shelf {
    public static String describe(Book book) {
        return book.title() + " — " + book.internalNote();
    }
}
```

А из другого пакета — нет:

```java,does_not_compile
package ru.example.app;

import ru.example.model.Book;

public class Bad {
    public static void main(String[] args) {
        System.out.println(new Book("x", 1).internalNote());
    }
}
```

```text
error: internalNote() is not public in Book;
       cannot be accessed from outside package
```

Пакетно-приватный уровень полезнее, чем кажется: он позволяет классам одного
пакета сотрудничать тесно, оставляя наружу только то, что нужно другим. Пакет
превращается из каталога в границу.

> **Современный подход:** `public` по умолчанию — распространённая привычка и
> плохая. Всё, что стало `public`, вы обязаны поддерживать: у этого появятся
> пользователи, и менять сигнатуру станет нельзя.
>
> Разумный порядок обратный: начинайте с самого закрытого уровня и расширяйте,
> когда понадобится. `private`, пока хватает; пакетно-приватный, когда нужен
> соседу; `public`, только когда это действительно часть внешнего лица вашего
> кода.
>
> `protected` используйте с осторожностью: он открывает внутренности всем
> наследникам, а наследование, как мы обсуждали в главе 6, само по себе связывает
> классы намертво.

## Как называют пакеты

По традиции — доменное имя организации наоборот: `com.google.gson`,
`org.apache.commons`, `ru.example.app`. Смысл в глобальной уникальности: домен
принадлежит одному владельцу, значит и пакет тоже.

Внутри пакеты обычно делят по **назначению**, а не по виду класса. `model`,
`storage`, `web` — лучше, чем `entities`, `services`, `controllers`: в первом
случае связанные вещи лежат рядом, во втором класс и то, что с ним работает,
раскиданы по трём каталогам.

## Зависимости

Про добавление зависимости в `pom.xml` мы говорили в главе 1. Теперь разберём,
что происходит дальше.

Библиотека, которую вы подключили, сама зависит от других. Maven обходит этот
граф целиком и скачивает всё — это **транзитивные зависимости**. Посмотреть их
можно так:

```console
$ mvn dependency:tree
```

Отсюда главная неприятность этой области — **конфликт версий**. Одна библиотека
требует версию 1.2 общей зависимости, другая — версию 2.0. В classpath может
быть только одна.

Maven разрешает конфликт правилом ближайшего: побеждает версия, до которой
короче путь в дереве. Работает это не всегда: библиотека, рассчитанная на 2.0,
получив 1.2, падает с `NoSuchMethodError` — и, что особенно неприятно, падает
**во время работы**, а не при сборке.

Лечится это явным указанием нужной версии в своём `pom.xml`: то, что объявлено у
вас, всегда побеждает.

## Модули

В Java 9 появилась модульная система. Идея в том, что пакетов для крупных систем
мало: пакет скрывает члены классов, но сам пакет доступен всем, кто подключил
ваш JAR.

Модуль описывается файлом `module-info.java` в корне исходников:

```java
module ru.example.app {
    requires java.net.http;

    exports ru.example.model;
}
```

`requires` перечисляет, что нужно модулю. `exports` — какие пакеты он открывает
наружу. Неперечисленные пакеты становятся недоступны извне, даже если классы в
них `public`.

> **Под капотом:** модули задумывались как большая перемена, а стали
> инструментом для узкого круга задач. Разделить на модули саму платформу Java
> получилось, и выигрыш ощутим: программе больше не нужен JDK целиком, можно
> собрать образ только из нужных частей, и он будет весить десятки мегабайт
> вместо сотен.
>
> А вот в прикладных проектах модули прижились слабо. Причина в том, что
> экосистема огромна, и модульным должен быть **весь** граф зависимостей: одна
> старая библиотека без `module-info` тянет всю сборку обратно в classpath.
>
> Практический вывод: знать про модули стоит, потому что сообщения об ошибках
> вроде `module java.base does not export sun.misc` встречаются. Начинать новый
> обычный проект с модулей — не обязательно.

## JAR

Результат сборки — **JAR**: обычный ZIP-архив с байт-кодом и описанием внутри.
Заглянуть можно любым архиватором.

Чтобы JAR запускался сам, в описании указывают главный класс, и тогда достаточно
`java -jar app.jar`. Для программы с зависимостями обычно собирают
«толстый» JAR, включающий их все, — иначе пользователю придётся собирать
classpath вручную.

> **Получилось:** вы понимаете, что пакет — это пространство имён и граница
> доступа, знаете все четыре уровня видимости и почему начинать стоит с самого
> закрытого. Знаете, как принято называть и делить пакеты. Понимаете, откуда
> берутся транзитивные зависимости и почему конфликт версий проявляется во время
> работы, а не при сборке. Представляете, что такое модули и почему их роль
> оказалась скромнее задуманной.
