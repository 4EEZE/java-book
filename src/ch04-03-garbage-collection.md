## Сборщик мусора

Мы разобрались, что объекты живут в куче. Осталось выяснить, кто их оттуда
убирает.

В Java — никто из тех, кого вы можете назвать по имени. Освобождением памяти
занимается **сборщик мусора**, часть виртуальной машины, и вручную повлиять на
него почти нельзя. Метода «удалить объект» в языке просто нет.

## Когда объект становится мусором

Критерий один: до объекта больше нельзя добраться по ссылкам.

```java
void main() {
    String text = new String("первый");
    text = new String("второй");
    IO.println(text);
}
```

```text
второй
```

После второй строки на объект `"первый"` не указывает ни одна переменная.
Добраться до него невозможно, значит, он мусор — и рано или поздно память из-под
него освободится.

Важное слово — «рано или поздно». Момент сборки не определён. Объект не
исчезает в тот миг, когда стал недостижим; он исчезнет, когда сборщик до него
дойдёт, а когда это случится, зависит от нагрузки, настроек и реализации JVM.

Из этого следует правило, которое экономит много времени: **не пытайтесь
управлять сборкой мусора**. Метод `System.gc()` существует, но это не команда, а
пожелание — виртуальная машина вправе его проигнорировать, и обычно так и
делает.

> **Под капотом:** практически все современные сборщики опираются на
> наблюдение, которое называют гипотезой о поколениях: подавляющее большинство
> объектов умирает молодыми. Поэтому куча делится на области, новые объекты
> попадают в «молодую», и её сборка — частая и дешёвая операция: живых объектов
> там мало, и достаточно скопировать их в другую область, а всю область целиком
> объявить свободной. То, что пережило несколько таких сборок, переезжает в
> «старую» область, где сборка редкая и дорогая.
>
> Отсюда контринтуитивный вывод: создать много короткоживущих объектов в Java
> дёшево. Оптимизировать код, избегая создания объектов «чтобы не нагружать
> сборщик», почти всегда преждевременно.

## Что сборщик не делает

Он освобождает **память** — и только её. Всё остальное, что удерживает
программа, приходится освобождать явно: открытые файлы, сетевые соединения,
подключения к базе данных. Их количество ограничено операционной системой, и
ждать, пока сборщик когда-нибудь доберётся до объекта, нельзя.

Раньше для этого писали `try`/`finally`. Сейчас есть конструкция короче —
`try` с ресурсами:

```java
void main() {
    try (var first = new Resource("первый");
         var second = new Resource("второй")) {
        IO.println("работаем");
        throw new RuntimeException("сбой");
    } catch (RuntimeException e) {
        IO.println("поймали: " + e.getMessage());
    }
}

class Resource implements AutoCloseable {
    private final String name;

    Resource(String name) {
        this.name = name;
        IO.println("открыт: " + name);
    }

    public void close() {
        IO.println("закрыт: " + name);
    }
}
```

```text
открыт: первый
открыт: второй
работаем
закрыт: второй
закрыт: первый
поймали: сбой
```

Разберём вывод, в нём три важные вещи.

**Ресурсы закрылись, хотя было выброшено исключение.** В этом весь смысл
конструкции: `close()` вызывается при любом выходе из блока — нормальном или
аварийном.

**Закрылись в обратном порядке.** Второй открыт последним и закрыт первым. Это
существенно, когда один ресурс зависит от другого.

**Закрылись до блока `catch`.** К моменту обработки исключения ресурсов уже нет.

Работает это для любого объекта, чей класс реализует `AutoCloseable` — как наш
`Resource`. Все классы стандартной библиотеки, связанные с файлами и сетью, его
реализуют.

Синтаксис классов мы разбираем в [главе 5](ch05-00-classes.md), а исключения — в главе 9. Здесь важна
мысль: **память освобождается сама, ресурсы — нет**.

## Утечки памяти в Java

Принято считать, что со сборщиком мусора утечек не бывает. Бывают — просто
выглядят иначе.

Утечка в Java — это объект, который давно не нужен, но на который всё ещё
существует ссылка. Сборщик видит, что до объекта можно добраться, и не трогает
его. С его точки зрения всё в порядке; это программа считает иначе.

```java,wrong_behavior
import java.util.ArrayList;
import java.util.List;

static final List<String> LOG = new ArrayList<>();

void main() {
    for (int i = 0; i < 5; i++) {
        handle("запрос " + i);
    }
    IO.println("записей в журнале: " + LOG.size());
}

void handle(String request) {
    LOG.add(request);
}
```

```text
записей в журнале: 5
```

Пять записей выглядят безобидно. Но `LOG` — статическое поле, оно живёт всё
время работы программы и ничего не удаляет. На сервере, обрабатывающем миллионы
запросов, этот список будет расти, пока не кончится память.

Типичные источники таких утечек: статические коллекции, кеши без ограничения
размера, подписки на события без отписки. Общее у них одно — ссылка живёт
дольше, чем нужен объект.

## Чего делать не нужно

**Не вызывайте `System.gc()`.** Это пожелание, которое обычно игнорируется, а
если не игнорируется — останавливает программу не вовремя.

**Не присваивайте `null`, чтобы «помочь сборщику».** Локальная переменная
исчезнет вместе с кадром метода. Писать `object = null;` в конце метода
бессмысленно.

**Не используйте `finalize()`.** Этот метод обещал код перед сборкой объекта,
но момент вызова не гарантирован, а иногда его не было вовсе. Метод объявлен
устаревшим и удаляется из языка. Для освобождения ресурсов есть `AutoCloseable`.

## Итоги

Вы понимаете, что переменная примитивного типа хранит
значение, а ссылочного — ссылку, и почему из этого следует всё остальное:
присваивание копирует ссылку, метод меняет переданный объект, но не может
перенаправить чужую переменную, `==` сравнивает объекты на тождество, а не на
равенство, `final` фиксирует имя, а не содержимое. Знаете, что такое `null`,
откуда берётся `NullPointerException` и как читать его сообщение. Знаете, что
память освобождается сама, а файлы и соединения — нет.
