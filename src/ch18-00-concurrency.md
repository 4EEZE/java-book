# Многопоточность

Самая коварная глава книги. Ошибки здесь не похожи на остальные: программа
компилируется, проходит тесты, работает месяцами — а потом один раз в неделю
выдаёт неверный результат, и повторить это не получается.

## Зачем

Поток — независимая последовательность выполнения. Нескольких потоков хотят по
двум разным причинам.

**Задействовать все ядра.** Вычисление, разложенное на восемь потоков, на
восьмиядерном процессоре идёт примерно вчетверо быстрее.

**Не ждать впустую.** Пока один поток ждёт ответа от сети, другие работают. Для
сервера это главное: почти всё время он ждёт.

## Поток

```java
Thread thread = new Thread(() -> IO.println("из другого потока"));
thread.start();
thread.join();
```

`start()` запускает поток и **сразу возвращается** — дальше два потока идут
параллельно. `join()` ждёт завершения.

Частая ошибка новичка — вызвать `run()` вместо `start()`. Метод `run()` просто
выполнит тело в текущем потоке, никакой параллельности не будет, и никакой
ошибки вы не увидите.

## Гонка

Теперь главное. Два потока увеличивают один счётчик по сто тысяч раз каждый:

```java,wrong_behavior
static int counter = 0;

void main() throws InterruptedException {
    Runnable work = () -> {
        for (int i = 0; i < 100_000; i++) {
            counter++;
        }
    };

    Thread t1 = new Thread(work);
    Thread t2 = new Thread(work);
    t1.start();
    t2.start();
    t1.join();
    t2.join();

    IO.println(counter);
}
```

Ожидается 200000. Три запуска подряд на моей машине:

```text
193235
194099
195892
```

Числа разные, и ни одно не верное. Часть увеличений пропала.

Причина в том, что `counter++` — не одно действие, а три: прочитать значение,
прибавить единицу, записать обратно. Между ними поток может быть прерван.

```text
поток 1: читает 100
поток 2: читает 100        ← оба прочли одно и то же
поток 1: пишет 101
поток 2: пишет 101         ← одно увеличение потеряно
```

Это **гонка**: результат зависит от того, в каком порядке потоки успели
выполнить свои шаги, а порядок непредсказуем.

Обратите внимание на самое неприятное свойство. Программа не падает. Она не
сообщает об ошибке. Она выдаёт правдоподобное число, которое почти правильное —
и заметить подвох можно только зная, каким оно должно быть.

## `synchronized`

Первое средство — запретить двум потокам одновременно входить в участок кода:

```java
static final Object lock = new Object();

synchronized (lock) {
    counter++;
}
```

```text
200000
```

`synchronized` захватывает **монитор** объекта. Пока один поток внутри, другие
ждут у входа. Три шага увеличения снова становятся неделимыми.

Тот же смысл имеет модификатор на методе:

```java
public synchronized void increment() {
    counter++;
}
```

Это сокращение для `synchronized (this)`.

Важно, что защищает не переменную, а **участок кода**, и только для тех, кто
захватывает тот же объект. Два места, синхронизированные по разным объектам, друг
другу не мешают — и защиты не получается.

## Атомарные операции

Для счётчиков есть решение проще и быстрее:

```java
static final AtomicInteger counter = new AtomicInteger();

counter.incrementAndGet();
```

```text
200000
```

Атомарные типы из `java.util.concurrent.atomic` выполняют «прочитать, изменить,
записать» как одно неделимое действие — на уровне процессорной инструкции, без
блокировки и ожидания.

Есть `AtomicInteger`, `AtomicLong`, `AtomicBoolean`, `AtomicReference`. Если
задача сводится к одной переменной, берите их: они и короче, и быстрее
`synchronized`.

## Видимость

Есть вторая беда, менее очевидная, чем гонка:

```java,wrong_behavior
static boolean running = true;

void main() throws InterruptedException {
    new Thread(() -> {
        while (running) { }
        IO.println("остановились");
    }).start();

    Thread.sleep(100);
    running = false;
}
```

Программа может **не завершиться никогда**, хотя `running` давно `false`. На
моей машине она и не завершается:

```text
флаг снят
(и дальше тишина — пришлось прерывать по таймауту)
```

Строка «остановились» не печатается: второй поток продолжает крутить пустой цикл,
не замечая, что флаг сняли.

Дело в том, что каждое ядро процессора работает со своим кешем, и записанное
одним потоком значение может не дойти до другого. Более того, компилятор и
процессор вправе переупорядочивать действия, если это не меняет результат для
**одного** потока.

Лечится словом `volatile`:

```java
static volatile boolean running = true;
```

`volatile` означает: читать и писать эту переменную только из общей памяти, не
кешировать, не переупорядочивать вокруг неё. Для флага-переключателя этого
достаточно.

Но `volatile` **не** делает операции атомарными: `counter++` на `volatile`-поле
по-прежнему теряет увеличения. Он решает задачу видимости, а не неделимости.

## Взаимная блокировка

Худшее, что случается с блокировками:

```java,wrong_behavior
// поток 1
synchronized (a) {
    synchronized (b) { ... }
}

// поток 2
synchronized (b) {
    synchronized (a) { ... }
}
```

Первый поток захватил `a` и ждёт `b`. Второй захватил `b` и ждёт `a`. Оба будут
ждать вечно.

Программа не падает и не сообщает ничего — она просто перестаёт отвечать.

Основное средство — **единый порядок захвата**: если все потоки берут блокировки
в одном и том же порядке, круговое ожидание невозможно. И общее правило: чем
меньше блокировок и чем они короче, тем меньше шансов.

## Не пишите потоки руками

> **Современный подход:** создавать `Thread` напрямую сегодня почти не нужно.
> Поток — дорогой ресурс, а управление их количеством вручную быстро
> превращается в отдельную задачу.
>
> Вместо этого берут **пул потоков**:
>
> ```java
> try (var pool = Executors.newFixedThreadPool(4)) {
>     for (Task task : tasks) {
>         pool.submit(() -> process(task));
>     }
> }
> ```
>
> Пул сам распределяет задачи по потокам и переиспользует их. `submit` возвращает
> `Future` — обещание результата, у которого можно спросить значение, дождавшись
> готовности.
>
> Ещё лучше — вовсе не делить изменяемое состояние. Неизменяемые объекты из глав
> 4 и 7 безопасны в многопоточной среде **по построению**: то, что нельзя
> изменить, нельзя и испортить гонкой. Задача, которая принимает данные и
> возвращает результат, ничего не меняя вокруг, не нуждается ни в
> `synchronized`, ни в `volatile`.
>
> Это самый надёжный подход из всех: не решать проблему совместного доступа, а
> устранять сам совместный доступ.

## Потокобезопасные коллекции

`ArrayList` и `HashMap` из [главы 8](ch08-00-collections.md) к параллельной работе не приспособлены.
Одновременное изменение из двух потоков испортит их внутреннее устройство — в
случае с `HashMap` дело доходило до зацикливания при чтении.

Для таких случаев есть готовые:

| Вместо | Берите |
|---|---|
| `HashMap` | `ConcurrentHashMap` |
| `ArrayList` | `CopyOnWriteArrayList` (при редкой записи) |
| очередь между потоками | `LinkedBlockingQueue` |

Оговорка: потокобезопасность коллекции относится к **отдельным операциям**.
Связка «проверить, потом положить» безопасной не становится — для этого у
`ConcurrentHashMap` есть `computeIfAbsent` и `putIfAbsent`, делающие оба шага
разом.

> **Под капотом:** почему всё это вообще нужно объяснять — ведь программа просто
> выполняет инструкции по порядку?
>
> Не выполняет. Ради скорости компилятор и процессор переставляют действия
> местами, держат значения в регистрах и кешах, объединяют записи. Для одного
> потока результат гарантированно тот же, что и без оптимизаций, — и потому вы
> их не замечаете.
>
> Многопоточность эту иллюзию ломает: другой поток видит происходящее без
> сглаживания. Правила о том, что именно один поток обязан увидеть из действий
> другого, описаны в спецификации языка и называются моделью памяти Java. Знать
> её целиком не нужно, но полезно помнить вывод: **без `synchronized`,
> `volatile` или атомарных типов никаких гарантий видимости у вас нет**.

## Итоги

Вы умеете запускать поток и дожидаться его. Понимаете, что
такое гонка, почему `counter++` не является одним действием и почему ошибка
проявляется не каждый раз. Знаете три средства — `synchronized`, атомарные
типы, `volatile` — и чем они отличаются. Знаете, что такое взаимная блокировка
и как её избегать. И главное: понимаете, что надёжнее всего не делить
изменяемое состояние вовсе.

Всё это досталось Java из времён, когда поток был дорогим ресурсом. В Java 21
это изменилось — о чём следующая глава.
