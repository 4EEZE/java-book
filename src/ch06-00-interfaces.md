# Интерфейсы и полиморфизм

В прошлой главе каждый класс был сам по себе. Теперь займёмся тем, ради чего
объектную модель в основном и используют: научим разные классы вести себя
одинаково там, где это нужно.

## Задача

Допустим, программа показывает каталог: книги и фильмы. Классы разные, а
печатать список надо одинаково.

Без общего механизма приходится писать по методу на каждый тип:

```java
void printBooks(Book[] books) {
    for (Book b : books) {
        System.out.println(b.describe());
    }
}

void printFilms(Film[] films) {
    for (Film f : films) {
        System.out.println(f.describe());
    }
}
```

Методы отличаются одним словом. Добавится третий тип — появится третья копия, и
исправлять формат вывода придётся в трёх местах.

Проблема не в том, что кода много. Проблема в том, что `printBooks` требует
именно `Book`, хотя пользуется от него единственной способностью — рассказать о
себе. Вот это «пользуется только одной способностью» и надо записать в коде.

## Интерфейс

**Интерфейс** — список того, что объект умеет, без единого слова о том, как он
это делает:

<span class="filename">Файл: Describable.java</span>

```java
public interface Describable {
    String describe();
}
```

У метода нет тела — только подпись и точка с запятой. Интерфейс не говорит, как
описывать; он говорит, что описывать умеют.

Класс заявляет, что подходит под интерфейс, словом `implements`:

<span class="filename">Файл: Book.java</span>

```java
public class Book implements Describable {
    private final String title;
    private final int year;

    public Book(String title, int year) {
        this.title = title;
        this.year = year;
    }

    @Override
    public String describe() {
        return "книга «" + title + "», " + year;
    }
}
```

<span class="filename">Файл: Film.java</span>

```java
public class Film implements Describable {
    private final String title;
    private final int minutes;

    public Film(String title, int minutes) {
        this.title = title;
        this.minutes = minutes;
    }

    @Override
    public String describe() {
        return "фильм «" + title + "», " + minutes + " мин";
    }
}
```

`@Override` — **аннотация**. Она ничего не делает во время работы программы, но
просит компилятор проверить: этот метод действительно должен что-то
переопределять. Опечатались в имени — и вместо «метод не реализован» на этапе
компиляции вы получите молчаливо неработающую программу. Писать `@Override`
стоит всегда.

Теперь один метод обслуживает оба класса:

<span class="filename">Файл: Main.java</span>

```java
public class Main {
    public static void main(String[] args) {
        Describable[] catalog = {
            new Book("Идиот", 1869),
            new Film("Сталкер", 163)
        };

        printAll(catalog);
    }

    static void printAll(Describable[] items) {
        for (Describable item : items) {
            System.out.println(item.describe());
        }
    }
}
```

```text
книга «Идиот», 1869
фильм «Сталкер», 163 мин
```

Это и есть **полиморфизм**: переменная объявлена как `Describable`, а хранит то
книгу, то фильм, и `describe()` вызывается тот, который принадлежит настоящему
объекту.

Обратите внимание на важное: выбор метода происходит **во время работы**
программы, а не при компиляции. Компилятор знает только, что у `item` есть
`describe()`. Какой именно — решается в момент вызова, по фактическому типу
объекта. Это называется динамической диспетчеризацией и составляет всю суть
полиморфизма.

Добавить третий тип теперь стоит одного класса. `printAll` менять не нужно —
он и не знал, с чем работает.

## Чего интерфейс не позволяет

Интерфейс нельзя создать:

```java,does_not_compile
Describable d = new Describable();
```

```text
error: Describable is abstract; cannot be instantiated
```

Разумно: непонятно, что должен вернуть `describe()` у объекта, который ничего
собой не представляет.

И нельзя заявить реализацию, не реализовав:

```java,does_not_compile
public class Magazine implements Describable {
}
```

```text
error: Magazine is not abstract and does not override abstract method
       describe() in Describable
```

Это ценное свойство: интерфейс — обещание, а компилятор следит, чтобы обещание
выполнялось.

## Методы по умолчанию

Иногда у способности есть очевидная реализация, и требовать её от каждого класса
незачем. Такой метод помечают `default` и пишут прямо в интерфейсе:

<span class="filename">Файл: Describable.java</span>

```java
public interface Describable {
    String describe();

    default String shortLabel() {
        return describe().toUpperCase();
    }
}
```

```text
книга «Идиот», 1869 / КНИГА «ИДИОТ», 1869
фильм «Сталкер», 163 мин / ФИЛЬМ «СТАЛКЕР», 163 МИН
```

`shortLabel()` доступен всем реализациям, хотя ни в `Book`, ни в `Film` его нет.
Класс при желании может его переопределить.

Заметьте, что `default`-метод вызывает `describe()`, не имея понятия, как тот
устроен. Интерфейс опирается на собственное обещание.

> **Под капотом:** методы по умолчанию появились в Java 8 не ради удобства, а
> ради совместимости. Когда в язык добавляли потоки данных (глава 15),
> интерфейсу `Collection` понадобился метод `stream()`. Добавить в интерфейс
> обычный метод означало сломать всякий существующий класс, который его
> реализует, — а таких в мире миллионы. `default` позволил расширить интерфейс,
> не ломая никого: старый код продолжил компилироваться, новый получил метод.
>
> Из этого следует и то, как их применять: `default` хорош для расширения уже
> опубликованного интерфейса и для удобных надстроек над основными методами. Он
> плох как способ раздать классам общее состояние — состояния у интерфейса нет
> и быть не может.

## Абстрактные классы

У интерфейсов есть родственник — **абстрактный класс**. Он тоже не создаётся
напрямую и тоже может требовать реализации методов, но в отличие от интерфейса
имеет поля и конструктор:

<span class="filename">Файл: Shape.java</span>

```java
public abstract class Shape {
    private final String name;

    protected Shape(String name) {
        this.name = name;
    }

    public abstract double area();

    public String report() {
        return name + ": " + area();
    }
}
```

<span class="filename">Файл: Circle.java</span>

```java
public class Circle extends Shape {
    private final double radius;

    public Circle(double radius) {
        super("круг");
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
```

```text
круг: 3.141592653589793
```

Новое здесь: `extends` вместо `implements` — класс **наследует** абстрактный
класс. `super("круг")` вызывает конструктор родителя и обязан быть первой
инструкцией. `protected` — уровень доступа между `private` и `public`: видно
наследникам.

Правило выбора между интерфейсом и абстрактным классом простое:

|  | Интерфейс | Абстрактный класс |
|---|---|---|
| Поля с состоянием | нет | да |
| Конструктор | нет | да |
| Сколько можно иметь одному классу | сколько угодно | ровно один |

Последняя строка обычно и решает. Класс наследует **один** класс, но реализует
сколько угодно интерфейсов, поэтому интерфейс — выбор по умолчанию, а
абстрактный класс берут, когда наследникам действительно нужно общее состояние.

## Наследование и почему с ним осторожны

`extends` работает и между обычными классами: наследник получает все поля и
методы родителя и может переопределить те, что ему не подходят.

Звучит как отличный способ переиспользовать код, и десятилетиями его так и
применяли. Опыт оказался неудачным.

> **Современный подход:** наследование стоит использовать, только когда
> наследник действительно **является** разновидностью родителя и обязан быть
> с ним взаимозаменяем. Во всех остальных случаях — когда классу просто нужны
> чужие возможности — правильный инструмент не наследование, а **композиция**:
> держать нужный объект полем и обращаться к нему.
>
> Причина в том, что наследование связывает классы намертво. Наследник зависит
> не только от того, что родитель делает, но и от того, **как** он это делает:
> стоит родителю в новой версии начать вызывать один свой метод из другого — и
> наследник, переопределивший один из них, ломается, хотя в нём ничего не
> меняли. Это называют хрупкостью базового класса.
>
> Практическое правило: `extends` только тогда, когда фраза «наследник — это
> разновидность родителя» звучит осмысленно и остаётся верной во всех местах,
> где родитель используется. Не подходит — делайте поле. В стандартной
> библиотеке Java есть образцовый контрпример: `java.util.Stack` наследует
> `Vector`, и из-за этого у стека есть метод «вставить элемент в середину».
> Пользоваться `Stack` из-за этого не рекомендуют до сих пор.

## Проверка типа

Иногда полиморфизма мало: нужно узнать, что за объект пришёл, и поступить
по-разному. Для этого есть `instanceof`:

```java
static String label(Object o) {
    if (o instanceof String s) {
        return "строка длиной " + s.length();
    } else if (o instanceof Integer n) {
        return "число " + (n * 2);
    }
    return "что-то ещё";
}
```

```text
строка длиной 6
число 42
что-то ещё
```

Обратите внимание на запись `o instanceof String s`: если проверка прошла,
переменная `s` сразу доступна и уже имеет тип `String`. Приводить тип отдельно
не нужно.

Так было не всегда. Раньше писали в два шага:

```java
if (o instanceof String) {
    String s = (String) o;
    return "строка длиной " + s.length();
}
```

Тип упоминался трижды, и вторая строка могла упасть, если в первой опечатались.
Сопоставление с образцом, появившееся в Java 16, эту возню убрало — и это
только начало, потому что образцы умеют гораздо больше. Им посвящена глава 7.

Оговорка: длинная цепочка `instanceof` обычно означает, что полиморфизм
применили не там, где следовало. Если проверок много и они разбросаны по коду,
подумайте, не должен ли каждый класс сам знать, что ему делать.

## Интерфейсы из стандартной библиотеки

Свои интерфейсы вы будете писать не каждый день, а вот реализовывать чужие —
постоянно. Самый частый — `Comparable`: он означает «объекты этого класса можно
упорядочить».

<span class="filename">Файл: Book.java</span>

```java
public class Book implements Comparable<Book> {
    private final String title;
    private final int year;

    public Book(String title, int year) {
        this.title = title;
        this.year = year;
    }

    @Override
    public int compareTo(Book other) {
        return Integer.compare(this.year, other.year);
    }

    @Override
    public String toString() {
        return title + " (" + year + ")";
    }
}
```

```java
Book[] books = { new Book("Мы", 1920), new Book("Идиот", 1869) };
Arrays.sort(books);
System.out.println(Arrays.toString(books));
```

```text
[Идиот (1869), Мы (1920)]
```

`compareTo` возвращает отрицательное число, если текущий объект меньше другого,
положительное — если больше, ноль — если они равны по порядку. Считать разность
вручную (`this.year - other.year`) не стоит: на больших числах она переполнится,
как мы разбирали в главе 3. `Integer.compare` делает это правильно.

Реализовав один метод, класс получил работающую сортировку — `Arrays.sort`
ничего не знает о книгах, он знает только `Comparable`. Это ровно тот же приём,
что и наш `printAll`, только написанный не нами.

`<Book>` в угловых скобках — обобщённый тип: так мы сказали, что сравниваемся
именно с книгами. Обобщённым типам посвящена глава 10.

> **Получилось:** вы умеете объявлять интерфейс и реализовывать его, понимаете,
> что метод выбирается по фактическому типу объекта во время работы программы, и
> знаете, зачем нужна `@Override`. Различаете интерфейс и абстрактный класс и
> знаете правило выбора между ними. Понимаете, почему наследование применяют
> осторожно и что такое композиция. Умеете проверять тип через `instanceof` с
> образцом и реализовали `Comparable`, получив бесплатную сортировку.

Мы не раз сказали, что подробности будут в главе 7 — про образцы и про то, как
описывать данные без церемоний. Пора туда.
