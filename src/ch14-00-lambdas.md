# Лямбды и функциональные интерфейсы

Лямбды встречались нам уже несколько раз: `removeIf(s -> s.equals("а"))` в главе
8, `assertThrows(..., () -> new Money(-1))` в [главе 12](ch12-00-testing.md), `Entry::count` и
`Integer::sum` в [главе 13](ch13-00-cli-project.md). Каждый раз мы отсылали сюда.

## Задача: передать поведение

Метод может принять число, строку, список. А можно ли передать в метод
**действие** — то, что он должен сделать?

Пример: отсортировать список строк по длине. Сортировка уже написана, менять её
не нужно; ей не хватает только знания о том, что считать «меньше».

До Java 8 это записывали так:

```java
List<String> items = new ArrayList<>(List.of("ббб", "а", "вв"));

items.sort(new Comparator<String>() {
    @Override
    public int compare(String x, String y) {
        return Integer.compare(x.length(), y.length());
    }
});

IO.println(items);
```

```text
[а, вв, ббб]
```

Это **анонимный класс** — класс без имени, объявленный прямо на месте. Работает,
но соотношение полезного к служебному удручает: содержательна одна строка, а
написано шесть.

## Лямбда

Лямбда — та же мысль без обёртки:

```java
items.sort((x, y) -> Integer.compare(x.length(), y.length()));
```

```text
[а, вв, ббб]
```

Одна строка вместо шести, и в ней нет ничего лишнего.

Разберём синтаксис. Слева от стрелки — параметры, справа — тело.

```java
() -> "результат"                    // без параметров
x -> x * 2                           // один параметр, скобки необязательны
(x, y) -> x + y                      // два параметра
(x, y) -> {                          // тело из нескольких инструкций
    int sum = x + y;
    return sum * 2;
}
```

Типы параметров не пишут: компилятор выводит их из контекста. В `items.sort(...)`
он знает, что список строковый, значит `x` и `y` — строки.

Если тело — одно выражение, `return` не нужен: значение выражения и есть
результат. Если тело в фигурных скобках, `return` обязателен.

## Функциональный интерфейс

Возникает вопрос: какой у лямбды тип?

Ответ неожиданный: лямбда — это реализация интерфейса, у которого ровно **один**
абстрактный метод. Такой интерфейс называют **функциональным**.

`Comparator` из примера — именно такой: у него один метод `compare`. Записывая
лямбду, мы создаём объект, реализующий этот метод.

Свой функциональный интерфейс объявляется обычным образом:

<span class="filename">Файл: Validator.java</span>

```java
@FunctionalInterface
public interface Validator {
    boolean isValid(String value);
}
```

```java
Validator notEmpty = s -> !s.isEmpty();
Validator isNumber = s -> s.matches("\\d+");

IO.println(notEmpty.isValid("текст"));
IO.println(isNumber.isValid("abc"));
```

```text
true
false
```

`@FunctionalInterface` — аннотация в духе `@Override` из [главы 6](ch06-00-interfaces.md): она ничего не
меняет, но просит компилятор проверить, что абстрактный метод действительно
один. Добавите второй — получите ошибку компиляции сразу, а не в месте, где
перестанет работать лямбда.

## Готовые интерфейсы

Свои функциональные интерфейсы нужны редко: для большинства случаев они уже есть
в пакете `java.util.function`.

| Интерфейс | Метод | Смысл |
|---|---|---|
| `Function<T, R>` | `apply` | из `T` делает `R` |
| `Predicate<T>` | `test` | проверяет условие |
| `Consumer<T>` | `accept` | принимает и ничего не возвращает |
| `Supplier<T>` | `get` | ничего не принимает и выдаёт значение |
| `BiFunction<T, U, R>` | `apply` | из двух значений делает третье |
| `UnaryOperator<T>` | `apply` | из `T` делает `T` |

```java
Function<String, Integer> length = s -> s.length();
Predicate<String> isEmpty = s -> s.isEmpty();
Consumer<String> print = s -> IO.println(s);
Supplier<String> make = () -> "создано";

IO.println(length.apply("привет"));
IO.println(isEmpty.test(""));
print.accept("через Consumer");
IO.println(make.get());
```

```text
6
true
через Consumer
создано
```

Имена методов у них разные — `apply`, `test`, `accept`, `get`, — и запоминать их
приходится. Утешает то, что вызывать эти методы вручную почти не придётся: обычно
лямбда сразу передаётся в чужой метод.

## Ссылки на методы

Присмотритесь к лямбдам выше: некоторые не делают ничего своего, а лишь вызывают
готовый метод.

```java
Function<String, Integer> length = s -> s.length();
```

Для такого случая есть более короткая запись — **ссылка на метод**:

```java
Function<String, Integer> length = String::length;
```

Двоеточий два, аргументы не пишутся вовсе. Читается как «вот метод, вызывайте
его сами».

Видов ссылок четыре:

```java
String::length          // метод объекта, который придёт аргументом
IO::println             // метод конкретного объекта или класса
Integer::parseInt       // статический метод
ArrayList::new          // конструктор
```

Первые два различить непросто, и это нормально: компилятор разбирается сам, а на
практике вы пишете то, что читается, и проверяете, что собралось.

Именно эти записи встречались в прошлых главах: `Integer::sum` в подсчёте слов,
`Entry::count` в сортировке.

> **Современный подход:** ссылка на метод короче лямбды, но не всегда понятнее.
> `String::length` читается хорошо. `Foo::bar` в незнакомом коде — хуже, чем
> `foo -> foo.bar()`, потому что во втором случае видно, что на что действует.
>
> Разумное правило: берите ссылку, когда имя метода само объясняет
> происходящее, и оставляйте лямбду, когда важнее показать, откуда берётся
> аргумент. Цель — читаемость, а не краткость. Это то же рассуждение, что про
> `var` в [главе 3](ch03-00-common-concepts.md).

## Лямбда помнит окружение

Лямбда видит переменные того места, где написана:

```java
String prefix = "Привет, ";
Function<String, String> greet = name -> prefix + name;

IO.println(greet.apply("Аня"));
```

```text
Привет, Аня
```

Переменная `prefix` не передавалась в лямбду — она **захвачена** из окружения.
Такое поведение называют замыканием.

Но есть ограничение:

```java,does_not_compile
int count = 0;
Supplier<Integer> get = () -> count;
count = 5;
```

```text
error: local variables referenced from a lambda expression must be final or
       effectively final
    Supplier<Integer> get = () -> count;
                                  ^
```

Захватываемая переменная обязана быть **фактически финальной** — то есть не
меняться после присваивания. Писать `final` не нужно, достаточно её не трогать.

Причина в [главе 4](ch04-00-references.md). Лямбда может пережить метод, в котором создана: её сохранят в
поле, передадут в другой поток, вызовут через час. А локальная переменная живёт в
кадре вызова, который к тому времени уничтожен. Поэтому лямбда получает не саму
переменную, а её копию — и если бы оригинал менялся, копия молча разошлась бы с
ним.

Обойти ограничение можно, но обычно не нужно: если значение должно меняться, ему
место в поле объекта или в возвращаемом результате, а не в захваченной локальной
переменной.

> **Под капотом:** лямбда — не анонимный класс с укороченной записью, хотя
> ведёт себя похоже. Анонимный класс компилируется в отдельный `.class`-файл, и
> при каждом выполнении создаётся объект. Лямбда компилируется в специальную
> инструкцию байт-кода, и реализацию виртуальная машина создаёт сама при первом
> обращении — а лямбду без захваченных переменных может переиспользовать, не
> создавая объект заново.
>
> Практический вывод один: лямбды дешевле анонимных классов, и избегать их из
> опасений за скорость не нужно.

## Итоги

Вы понимаете, что лямбда — это реализация интерфейса с
единственным абстрактным методом, и умеете её записывать во всех формах.
Знаете основные готовые интерфейсы из `java.util.function` и умеете
сокращать лямбду до ссылки на метод, когда это читается лучше. Понимаете,
что такое захват переменной и почему захватываемая обязана быть фактически
финальной.

Лямбды сами по себе — только половина дела. По-настоящему они раскрываются там,
где над данными выстраивают цепочку действий. Это следующая глава.
