# Ввод-вывод и файлы

Файл мы уже читали — в главе 13 одной строкой. Разберём эту область как следует:
что ещё бывает, где подстерегают неприятности и почему в Java два набора
инструментов для одного и того же.

## Путь — это не файл

```java
Path path = Path.of("данные.txt");
```

`Path` описывает **путь**, а не файл. Объект создаётся успешно, даже если по
этому пути ничего нет: это просто строка, разобранная на части и знающая правила
вашей операционной системы.

```java
IO.println(path.toAbsolutePath());
IO.println(path.getFileName());
IO.println(Files.exists(path));
```

Отделять путь от файла полезно: путь можно составлять, разбирать и передавать, не
трогая диск. Сборка пути делается через `resolve`, а не склейкой строк:

```java
Path config = Path.of("/etc").resolve("app").resolve("settings.conf");
```

Склейка через `+` и `"/"` ломается на Windows, где разделитель другой. `resolve`
знает правила системы.

## Чтение и запись целиком

Самый частый случай — файл небольшой и нужен целиком:

```java
Files.writeString(path, "первая\nвторая\nтретья\n");
IO.println(Files.readString(path).strip());
```

```text
первая
вторая
третья
```

Если нужны строки по отдельности:

```java
IO.println(Files.readAllLines(path));
```

```text
[первая, вторая, третья]
```

`writeString` по умолчанию **перезаписывает** файл целиком. Чтобы дописать в
конец, это надо сказать явно:

```java
Files.writeString(path, "четвёртая\n", StandardOpenOption.APPEND);
```

Умолчание выбрано удачно: случайно затереть файл неприятно, но заметно сразу, а
случайно дописать — незаметно и потому хуже.

## Когда файл большой

`readString` и `readAllLines` загружают файл в память целиком. Для конфигурации
это правильно, для журнала на десять гигабайт — нет.

Для больших файлов есть ленивое чтение:

```java
try (Stream<String> lines = Files.lines(path)) {
    IO.println(lines.filter(line -> line.startsWith("в")).toList());
}
```

```text
[вторая]
```

Здесь сходятся три вещи из прошлых глав. Это поток из главы 15 — со всей его
ленивостью: строки читаются по мере надобности, а не все сразу. Это `try` с
ресурсами из главы 4 — и он здесь **обязателен**: за потоком строк стоит
открытый файл, а его надо закрыть. И это `filter` с лямбдой из главы 14.

Забыть `try` с ресурсами легко, потому что программа будет работать: файловый
дескриптор просто останется занятым. На сотне вызовов вы этого не заметите, на
десятках тысяч — получите «слишком много открытых файлов».

Правило: **если метод возвращает поток, связанный с файлом, оборачивайте его в
`try` с ресурсами**. Обычные потоки от коллекций закрывать не нужно.

## Кодировка

```java
IO.println(Charset.defaultCharset());
```

```text
UTF-8
```

Начиная с Java 18 кодировка по умолчанию — UTF-8 на всех платформах. До этого
она зависела от системы, и один и тот же код на Windows и Linux читал файлы
по-разному: классическая причина «у меня работает, а у тебя кракозябры».

Все методы `Files` используют UTF-8, если не сказано иное. Когда файл в другой
кодировке, её указывают явно:

```java
Files.readString(path, Charset.forName("windows-1251"));
```

Правило простое: свои файлы всегда пишите в UTF-8, а кодировку чужих узнавайте
заранее и указывайте явно. Кодировка — не то, о чём стоит догадываться.

## Обход каталога

```java
try (Stream<Path> entries = Files.list(Path.of("."))) {
    entries.filter(Files::isRegularFile)
           .map(Path::getFileName)
           .forEach(IO::println);
}
```

`Files.list` даёт содержимое одного каталога, `Files.walk` — всё дерево
рекурсивно. Оба возвращают поток, связанный с файловой системой, поэтому снова
`try` с ресурсами.

Полезные проверки: `Files.exists`, `Files.isDirectory`, `Files.isRegularFile`,
`Files.size`.

## Два набора инструментов

В Java два способа работать с файлами, и это сбивает с толку.

**Старый** — `java.io.File`, из первой версии языка. Опознаётся по классам
`File`, `FileReader`, `BufferedReader`, `FileInputStream`.

**Новый** — `java.nio.file`, появился в Java 7. Это `Path` и `Files`, которыми мы
пользуемся здесь.

> **Современный подход:** для новых программ берите `java.nio.file`. Старый
> набор не то чтобы сломан, но у него есть неприятное свойство: методы вроде
> `file.delete()` возвращают `false` при неудаче и **не говорят почему** — не
> было прав, файл не существовал, каталог не пуст. `Files.delete()` в той же
> ситуации бросает исключение с внятным объяснением.
>
> Старый набор всё же придётся знать: он повсюду в существующем коде и в
> сигнатурах чужих библиотек. Переход между ними делается одним вызовом —
> `file.toPath()` и `path.toFile()`.
>
> Один случай, где старые классы остаются уместными, — чтение потока, который
> не является файлом: сетевое соединение, ввод пользователя, содержимое архива.
> Там `BufferedReader` по-прежнему основной инструмент.

## Потоки байтов и потоки символов

Ещё одно деление, которое стоит понимать.

**Байтовые потоки** (`InputStream`, `OutputStream`) работают с сырыми байтами:
картинки, архивы, любые двоичные данные.

**Символьные потоки** (`Reader`, `Writer`) работают с текстом и знают про
кодировку: они превращают байты в символы по заданным правилам.

Ошибка возникает, когда текст читают как байты и складывают в строку без
указания кодировки — тогда кириллица и рассыпается. Если данные текстовые,
работайте с текстом; если двоичные — не превращайте их в строку вовсе.

## Чего стоит остерегаться

**Файл может измениться между проверкой и использованием.** Связка
«проверить `Files.exists`, потом открыть» ненадёжна: между двумя вызовами файл
могут удалить. Правильнее просто открыть и обработать исключение — это и короче,
и честнее.

**Запись не атомарна.** Если программа прервётся посередине `writeString`,
файл останется испорченным наполовину. Когда это недопустимо, пишут во
временный файл рядом и затем переименовывают: переименование в пределах одной
файловой системы атомарно.

```java
Path temp = Path.of("данные.txt.tmp");
Files.writeString(temp, content);
Files.move(temp, path, StandardCopyOption.ATOMIC_MOVE,
                       StandardCopyOption.REPLACE_EXISTING);
```

**Относительные пути зависят от того, откуда запущена программа**, а не от того,
где лежит её код. Это постоянный источник недоумения: в IDE работает, из
терминала — нет.

> **Получилось:** вы понимаете, что `Path` описывает путь, а не файл, и умеете
> составлять пути через `resolve`. Умеете читать и писать файл целиком и по
> строкам, знаете, что `writeString` перезаписывает, и умеете дописывать.
> Понимаете, когда нужно ленивое чтение и почему поток от файла обязан быть в
> `try` с ресурсами. Знаете про UTF-8 по умолчанию с Java 18 и почему кодировку
> чужих файлов указывают явно. Различаете старый `java.io` и новый
> `java.nio.file` и знаете, какой брать.
