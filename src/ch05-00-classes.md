# Классы и объекты

До сих пор мы обходились числами, строками и массивами. Этого хватает, пока
данных мало. Посмотрим, что происходит, когда их становится больше.

Допустим, программа работает с книгами: у каждой есть название, автор и год.
Без классов пришлось бы держать три массива и следить, чтобы индексы совпадали:

```java
String[] titles = {"Идиот", "Мы"};
String[] authors = {"Достоевский", "Замятин"};
int[] years = {1869, 1920};
```

Формально это работает. Практически — каждое добавление книги требует трёх
согласованных правок, а перепутанный индекс даёт «Идиота» Замятина, и никакой
компилятор об этом не скажет.

Класс позволяет сказать прямо: название, автор и год — это одна вещь.

## Сначала — про файлы

В [главе 1](ch01-00-getting-started.md) мы договорились, что до разговора о классах пользуемся короткой формой
записи, а потом перейдём на полную. Момент настал, и причина у перехода не
стилистическая.

Возьмём компактный файл и попробуем закрыть поле от посторонних:

```java,wrong_behavior
class Account {
    private int balance = 100;
}

void main() {
    IO.println(new Account().balance);
}
```

```text
100
```

Поле помечено `private`, а прочиталось снаружи безо всяких возражений.

Дело в том, что компактный файл — это на самом деле один класс, который
компилятор достраивает сам. Объявленный в нём `class Account` оказывается
**вложенным** в этот неявный класс, а внутри одного класса `private` ничего не
закрывает: он ограничивает доступ границей класса верхнего уровня, и оба
оказались внутри неё.

Тот же код в обычных файлах ведёт себя как положено:

<span class="filename">Файл: Account.java</span>

```java
public class Account {
    private int balance = 100;
}
```

<span class="filename">Файл: Main.java</span>

```java,does_not_compile
public class Main {
    public static void main(String[] args) {
        Account a = new Account();
        System.out.println(a.balance);
    }
}
```

```text
Main.java:4: error: balance has private access in Account
        System.out.println(a.balance);
                            ^
```

Вот теперь `private` работает. Поэтому с этой главы мы пишем классы в
отдельных файлах: иначе половина разговора об инкапсуляции окажется враньём.

Компилировать и запускать такое нужно в два шага, как мы разбирали в главе 1:

```console
$ javac -d out Account.java Main.java
$ java -cp out Main
```

## Объявление класса

<span class="filename">Файл: Book.java</span>

```java
public class Book {
    String title;
    String author;
    int year;
}
```

Это уже полноценный класс. `title`, `author`, `year` — его **поля**: данные,
которые есть у каждой книги.

Создадим книгу:

<span class="filename">Файл: Main.java</span>

```java
public class Main {
    public static void main(String[] args) {
        Book book = new Book();
        book.title = "Идиот";
        book.author = "Достоевский";
        book.year = 1869;

        System.out.println(book.title + " — " + book.author);
    }
}
```

```text
Идиот — Достоевский
```

`new Book()` создаёт объект в куче и возвращает ссылку на него — ровно то, что мы
разбирали в [главе 4](ch04-00-references.md). Точка обращается к полю.

## Поля имеют значения по умолчанию

В отличие от локальных переменных, поля инициализировать не обязательно:

```java
public class Point {
    int x;
    String label;
    boolean visible;
}
```

```text
0 / null / false
```

Числовые поля получают ноль, логические — `false`, ссылочные — `null`. Это то
самое исключение из правила об определённом присваивании, которое мы отмечали в
[главе 3](ch03-00-common-concepts.md): для полей значение по умолчанию есть, для локальных переменных — нет.

Удобно, но с подвохом: поле типа `String`, которое забыли заполнить, равно
`null`, и обращение к нему даст `NullPointerException` где-то далеко от места,
где его забыли заполнить.

## Конструкторы

Создавать объект, а потом заполнять его по одному полю — плохо по двум причинам.
Легко что-нибудь забыть, и между созданием и заполнением объект существует в
недоделанном виде.

**Конструктор** позволяет задать всё сразу:

<span class="filename">Файл: Book.java</span>

```java
public class Book {
    String title;
    String author;
    int year;

    Book(String title, String author, int year) {
        this.title = title;
        this.author = author;
        this.year = year;
    }
}
```

```java
Book book = new Book("Идиот", "Достоевский", 1869);
```

Конструктор отличается от метода двумя вещами: он называется точно как класс и у
него нет типа возвращаемого значения — даже `void` не пишут.

`this` — ссылка на объект, который сейчас создаётся. Здесь она нужна, чтобы
различить поле и параметр: они называются одинаково. Без `this` запись
`title = title` присвоила бы параметру самого себя, и поле осталось бы пустым —
компилятор на это, кстати, не пожалуется.

Называть параметры так же, как поля, — общепринятая практика в Java, и `this`
существует в том числе ради неё.

### Конструктор по умолчанию исчезает

Пока своего конструктора нет, Java даёт бесплатный — без аргументов. Именно им
мы пользовались, когда писали `new Book()`. Но стоит объявить свой, как
бесплатный пропадает:

```java,does_not_compile
Book book = new Book();
```

```text
error: constructor Book in class Book cannot be applied to given types;
  required: String,String,int
```

Логика в том, что если вы описали, как правильно создавать объект, то создавать
его мимо этого описания, скорее всего, не нужно.

### Несколько конструкторов

Конструкторы перегружаются так же, как методы, и могут вызывать друг друга через
`this(...)`:

```java
public class Book {
    String title;
    String author;
    int year;

    Book(String title, String author, int year) {
        this.title = title;
        this.author = author;
        this.year = year;
    }

    Book(String title, String author) {
        this(title, author, 0);
    }
}
```

Второй конструктор для книг с неизвестным годом. Вызов `this(...)` обязан быть
первой инструкцией конструктора.

## Методы объекта

Класс объединяет не только данные, но и то, что с ними делают:

<span class="filename">Файл: Book.java</span>

```java
public class Book {
    String title;
    String author;
    int year;

    Book(String title, String author, int year) {
        this.title = title;
        this.author = author;
        this.year = year;
    }

    String describe() {
        return title + " (" + author + ", " + year + ")";
    }

    boolean isOlderThan(Book other) {
        return this.year < other.year;
    }
}
```

```java
Book idiot = new Book("Идиот", "Достоевский", 1869);
Book we = new Book("Мы", "Замятин", 1920);

System.out.println(idiot.describe());
System.out.println(idiot.isOlderThan(we));
```

```text
Идиот (Достоевский, 1869)
true
```

Внутри метода к полям обращаются просто по имени: `title` означает «поле того
объекта, у которого вызвали метод». Писать `this.title` тоже можно, и это не
ошибка, но обычно `this` пишут только там, где без него неоднозначно, — как в
конструкторе.

В `isOlderThan` виден второй объект: `other.year`. Метод одного объекта может
свободно читать поля другого объекта того же класса.

Обратите внимание, что `describe()` не печатает, а возвращает строку. Это
осознанный выбор: метод, который печатает, годится ровно для консоли, а метод,
который возвращает, годится и для консоли, и для файла, и для теста.

## Инкапсуляция

Пока все поля открыты, любой код может присвоить им что угодно:

```java
Book book = new Book("Идиот", "Достоевский", 1869);
book.year = -5000;
```

Книга из минус пятидесятого века компилируется без возражений. Чтобы такого не
случалось, поля закрывают, а доступ дают через методы:

<span class="filename">Файл: Book.java</span>

```java
public class Book {
    private final String title;
    private final String author;
    private int year;

    public Book(String title, String author, int year) {
        this.title = title;
        this.author = author;
        setYear(year);
    }

    public String getTitle() {
        return title;
    }

    public int getYear() {
        return year;
    }

    public void setYear(int year) {
        if (year < -3000 || year > 2100) {
            throw new IllegalArgumentException("Сомнительный год: " + year);
        }
        this.year = year;
    }
}
```

Теперь напрямую до полей не добраться, а `setYear` проверяет значение и
отказывается принимать бессмысленное.

Разберём, что тут появилось.

`private` — поле видно только внутри своего класса. `public` — метод виден
отовсюду. Есть ещё два уровня доступа, и им место в [главе 17](ch17-00-modules.md) вместе с пакетами.

`final` у `title` и `author` означает, что после создания книги их не поменять.
Год менять можно — скажем, при исправлении ошибки в данных, — а название с
автором нет.

`getTitle`, `setYear` — **геттеры** и **сеттеры**. Названия с приставками `get`
и `set` в Java не просто традиция: на это соглашение опирается множество
библиотек, и отступать от него не стоит.

`throw new IllegalArgumentException(...)` прерывает выполнение с ошибкой.
Подробно про исключения — в [главе 9](ch09-00-error-handling.md); здесь важно, что проверка отвергает плохое
значение сразу, а не позволяет ему разойтись по программе.

Смысл инкапсуляции не в том, чтобы «спрятать данные», а в том, чтобы объект сам
отвечал за своё состояние. Пока поля открыты, следить за правильностью года
обязан каждый, кто трогает книгу. Когда закрыты — только сам класс, и проверку
достаточно написать в одном месте.

> **Современный подход:** писать геттер и сеттер к каждому полю не нужно, и это
> самая частая ошибка при знакомстве с инкапсуляцией. Класс, у которого на
> каждое поле есть `getX` и `setX`, ничем не лучше класса с открытыми полями —
> просто многословнее. Открывайте наружу то, что действительно нужно снаружи.
>
> Если же класс существует только чтобы хранить набор значений и менять их не
> предполагается, писать всё это руками вообще не надо: для таких случаев в Java
> есть **записи** (`record`), где поля, конструктор, геттеры, `equals`,
> `hashCode` и `toString` получаются из одной строки. Им посвящена [глава 7](ch07-00-records-and-patterns.md). Всё,
> что мы разбираем здесь, остаётся нужным для классов с поведением — но если вы
> ловите себя на написании класса из одних полей, вспомните про записи.

## `static`: принадлежит классу, а не объекту

Поле или метод, помеченные `static`, существуют в одном экземпляре на весь класс:

<span class="filename">Файл: Counter.java</span>

```java
public class Counter {
    private static int created = 0;
    private final int id;

    public Counter() {
        created++;
        id = created;
    }

    public int getId() {
        return id;
    }

    public static int getCreated() {
        return created;
    }
}
```

```java
new Counter();
new Counter();
Counter third = new Counter();

System.out.println(third.getId() + " из " + Counter.getCreated());
```

```text
3 из 3
```

У каждого объекта свой `id`, а `created` один на всех. Обратите внимание на
последнюю строку: `getCreated()` вызывается у **класса**, а не у объекта, —
объект ему не нужен.

Так же обращаются и к самому статическому полю, когда оно открыто:
`Counter.created`. Писать `third.created` тоже можно, и компилятор это
проглотит, но так делать не стоит: запись выглядит как обращение к полю
объекта, хотя поле общее, и читателя это вводит в заблуждение.

Отсюда же понятно, почему `main` объявляют как `static`: виртуальной машине надо
вызвать его до того, как появится хоть один объект.

Внутри `static`-метода нельзя обратиться к обычному полю: непонятно, у какого
объекта его брать. Компилятор скажет `non-static variable cannot be referenced
from a static context` — одна из первых ошибок, которую встречают все.

> **Под капотом:** при создании объекта всё происходит в строгом порядке:
> сначала вызывается конструктор родительского класса, затем выполняются
> инициализаторы полей в порядке их объявления в файле, и только потом — тело
> конструктора.
>
> Порядок объясняет неочевидное поведение. Если конструктор передаёт работу
> другому через `this(...)`, инициализаторы полей выполняются один раз — в том
> конструкторе, который никому не делегирует. А поле, объявленное **ниже** по
> файлу, ещё не инициализировано в момент, когда выполняется инициализатор
> поля, объявленного выше, — и равно значению по умолчанию, а не тому, что вы
> написали.

## Что дальше

Мы научились описывать вещи: у книги есть название и год, книга умеет
рассказать о себе. Но пока каждый класс существует сам по себе.

Настоящая сила объектной модели появляется, когда разные классы можно
использовать одинаково — когда коду, печатающему список, всё равно, книги там
или фильмы, лишь бы у них было название. Это называется полиморфизмом, и об этом
следующая глава.
