# Обработка ошибок

Начнём с вопроса: как метод сообщает, что у него не получилось?

Допустим, метод разбирает строку в число. Обычным значением ответить «не
получилось» невозможно: любое число — законный результат разбора. Вернуть ноль
нельзя, ноль означает ноль. Вернуть `-1` нельзя по той же причине.

Можно вернуть `null`, но тогда проверять результат обязан каждый вызывающий, а
забыть проверку легко — мы разбирали это в главе 4. К тому же `null` не
объясняет, что именно пошло не так.

**Исключение** решает задачу иначе: оно не возвращает ответ, а прерывает
обычный ход выполнения.

## `throw` и раскрутка стека

```java
void main() {
    IO.println("до");
    fail();
    IO.println("после");
}

void fail() {
    throw new IllegalStateException("что-то не так");
}
```

```text
до
Exception in thread "main" java.lang.IllegalStateException: что-то не так
	at Main.fail(Main.java:8)
	at Main.main(Main.java:3)
```

Обратите внимание: `после` не напечаталось. `throw` немедленно прекращает
выполнение метода и передаёт исключение наверх — тому, кто его вызвал. Если и
там никто не готов его обработать, выше — и так до самого верха.

Наверху ждёт виртуальная машина. Она печатает тип исключения, сообщение и
трассировку — путь вызовов, по которому исключение поднималось, — и завершает
программу.

Такой подъём называют **раскруткой стека**: помните кадры вызовов из главы 4?
Исключение уничтожает их один за другим, пока не найдёт обработчик.

Читать трассировку, как мы говорили в главе 2, полезно снизу вверх: последняя
строка — где всё началось, а первая строка с вашим файлом — где именно упало.

## `try` и `catch`

Чтобы исключение не дошло до самого верха, его перехватывают:

```java
void main() {
    try {
        int number = Integer.parseInt("абв");
        IO.println("разобрали: " + number);
    } catch (NumberFormatException e) {
        IO.println("не число: " + e.getMessage());
    }
    IO.println("программа продолжается");
}
```

```text
не число: For input string: "абв"
программа продолжается
```

`try` очерчивает участок, где ожидается неприятность. `catch` указывает тип
исключения и что делать.

Заметьте, что строка `IO.println("разобрали: ...")` не выполнилась. Исключение
прервало блок `try` на месте, а не по его завершении: всё после сбоя внутри
`try` пропускается.

У перехваченного исключения можно спросить подробности: `getMessage()` даёт
текст, `getClass()` — тип, `printStackTrace()` печатает трассировку.

## `finally`

Иногда нужен код, который выполнится обязательно — вышли мы из блока нормально
или через исключение:

```java
int safe() {
    try {
        throw new RuntimeException("сбой");
    } finally {
        IO.println("finally выполнился");
    }
}
```

```text
finally выполнился
Exception in thread "main" java.lang.RuntimeException: сбой
```

Исключение улетело наверх, но `finally` сработал до этого. Именно для такого
`finally` и существует: закрыть файл, освободить блокировку, вернуть соединение
в пул.

Когда исключение всё-таки перехвачено, порядок такой: сначала `catch`, потом
`finally`, потом выполнение продолжается после всей конструкции:

```java
try {
    IO.println("A");
    throw new RuntimeException("x");
} catch (RuntimeException e) {
    IO.println("B");
} finally {
    IO.println("C");
}
IO.println("D");
```

```text
A
B
C
D
```

`finally` выполняется последним из трёх блоков, но раньше всего, что идёт за
конструкцией.

## Ловушка: `return` в `finally`

А вот так делать нельзя:

```java,wrong_behavior
int compute() {
    try {
        return 1;
    } finally {
        return 2;
    }
}
```

```text
2
```

`return` из `finally` затирает результат, который уже был готов уйти из `try`.
Хуже того, так же затирается и **исключение**: если бы `try` выбросил
исключение, а `finally` сделал `return`, исключение молча исчезло бы.

Правило простое: в `finally` не должно быть ни `return`, ни `throw`, ни `break`
— только освобождение ресурсов.

Впрочем, для освобождения ресурсов `finally` сегодня почти не нужен: есть `try`
с ресурсами, который мы разбирали в главе 4. Он короче и не даёт забыть
`close()`.

## Как устроены исключения

Все исключения — объекты, и у них есть иерархия:

```text
Throwable
├── Error                    системный сбой, не ловим
│   ├── OutOfMemoryError
│   └── StackOverflowError
└── Exception                ошибка, с которой можно что-то сделать
    ├── IOException          проверяемое
    ├── SQLException         проверяемое
    └── RuntimeException     непроверяемое
        ├── NullPointerException
        ├── IllegalArgumentException
        ├── IndexOutOfBoundsException
        └── NumberFormatException
```

Деление на три ветки — не формальность, у каждой своя роль.

**`Error`** означает, что сломалась сама среда: кончилась память, переполнился
стек. Ловить их не нужно: сделать с этим из программы почти нечего.

**`RuntimeException`** — ошибка в логике программы. `NullPointerException`,
выход за границу массива, неверный аргумент. Такие исключения означают, что
программу надо **исправить**, а не обработать.

**Остальные наследники `Exception`** — ожидаемые неприятности внешнего мира:
файла нет, сеть недоступна, база отказала. Программа написана правильно, просто
мир оказался не в том состоянии.

## Проверяемые и непроверяемые

Вот здесь Java отличается почти от всех языков, и об этом стоит знать
подробно.

Исключения, унаследованные от `Exception`, но **не** от `RuntimeException`,
называются **проверяемыми**. Компилятор требует либо перехватить их, либо
объявить, что метод их выбрасывает:

```java,does_not_compile
import java.nio.file.*;

void main() {
    String text = Files.readString(Path.of("нет.txt"));
}
```

```text
error: unreported exception IOException; must be caught or declared to be thrown
    String text = Files.readString(Path.of("нет.txt"));
                                  ^
```

Компилятор не даёт проигнорировать возможность, что файла нет. Вариантов два.

Перехватить:

```java
try {
    String text = Files.readString(Path.of("нет.txt"));
} catch (IOException e) {
    IO.println("не прочитали: " + e.getMessage());
}
```

Или объявить через `throws`, передав ответственность вызывающему:

```java
String read() throws IOException {
    return Files.readString(Path.of("нет.txt"));
}
```

`throws` в подписи — часть обещания метода наравне с типом результата: «я могу
не справиться, и вот почему». Тот, кто вызывает `read()`, обязан что-то с этим
сделать.

`RuntimeException` и его наследники — **непроверяемые**: их можно не
объявлять и не ловить. Компилятор молчит, потому что иначе `throws
NullPointerException` пришлось бы писать буквально везде.

> **Под капотом:** проверяемые исключения — уникальный эксперимент Java, и
> повторять его не стал почти никто: ни C#, ни Kotlin, ни Scala. Идея разумная:
> компилятор не даст забыть про предсказуемый сбой. На практике выяснились два
> изъяна.
>
> Первый: `throws` расползается по коду. Метод, вызывающий метод, который может
> не справиться, обязан либо ловить, либо объявлять — и объявление тянется через
> все уровни вверх.
>
> Второй, и он серьёзнее: под давлением компилятора программисты стали писать
> пустой `catch`, лишь бы он не жаловался. Проверяемое исключение, задуманное
> как страховка, превратилось в шум, который заглушают. Kotlin, выросший
> вплотную к Java, отказался от проверяемых исключений именно по этой причине.
>
> Это не значит, что их надо избегать. Это значит, что лишь наличие `throws`
> ничего не гарантирует: важно, что вы делаете в `catch`.

## Несколько видов ошибок

Один `try` может иметь несколько `catch`. Проверяются они сверху вниз, и
срабатывает первый подходящий:

```java
try {
    process(input);
} catch (NumberFormatException e) {
    IO.println("не число");
} catch (IOException e) {
    IO.println("проблема с файлом");
}
```

Порядок важен, и компилятор за ним следит: узкий тип обязан идти раньше
широкого.

```java,does_not_compile
try {
    throw new IllegalArgumentException("x");
} catch (RuntimeException e) {
    IO.println("широкий");
} catch (IllegalArgumentException e) {
    IO.println("узкий");
}
```

```text
error: exception IllegalArgumentException has already been caught
    } catch (IllegalArgumentException e) {
      ^
```

`RuntimeException` забрал бы всё, включая `IllegalArgumentException`, и вторая
ветка стала бы недостижимой. Это та же логика, что у образцов в `switch` из
главы 7, — и там компилятор говорит почти то же самое.

Если разные виды обрабатываются одинаково, их перечисляют через вертикальную
черту:

```java
try {
    IO.println("ок: " + check(value));
} catch (TooOldException | NumberFormatException e) {
    IO.println(e.getClass().getSimpleName() + ": " + e.getMessage());
}
```

```text
TooOldException: слишком старая книга: 1500
NumberFormatException: For input string: "abc"
ок: 1900
```

## Своё исключение

Исключение — обычный класс, и своё объявляется наследованием:

<span class="filename">Файл: TooOldException.java</span>

```java
public class TooOldException extends Exception {
    private final int year;

    public TooOldException(int year) {
        super("слишком старая книга: " + year);
        this.year = year;
    }

    public int year() {
        return year;
    }
}
```

`extends Exception` делает исключение проверяемым; `extends RuntimeException`
— непроверяемым. `super(...)` передаёт сообщение родителю, и оно потом
доступно через `getMessage()`.

Своё исключение имеет смысл, когда вызывающему нужно **различать** причину
сбоя, а не просто узнать о нём, — или когда вместе с сообщением нужны данные,
как поле `year` здесь.

Если различать не нужно, берите готовые: `IllegalArgumentException` для плохого
аргумента, `IllegalStateException` для неподходящего состояния объекта. Плодить
свои классы на каждый случай не стоит.

## Что ловить, а что нет

Это самое важное в главе, и здесь мы возвращаемся к обещанию из главы 2. Там
наша игра ушла в бесконечный цикл ровно потому, что `catch` был слишком широким:
он поймал `NumberFormatException`, означавшее конец ввода, и превратил внятную
аварию в тихое неправильное поведение.

> **Современный подход:** перехватывайте исключение **только если знаете, что с
> ним делать**. Годных вариантов немного:
>
> - **повторить** — сеть подвела, попробуем ещё раз;
> - **подставить запасное значение** — настройка не прочиталась, берём
>   значение по умолчанию;
> - **сообщить понятно** — пользователю нужно объяснение, а не трассировка;
> - **перевести в другой вид** — сохранив исходную причину, о чём ниже.
>
> Если ни один не подходит, не ловите. Исключение, прошедшее наверх, остановит
> программу с внятным сообщением, и это лучше, чем продолжение работы в
> испорченном состоянии. Неперехваченное исключение — не провал, а поведение по
> умолчанию, и оно разумное.

Три антипаттерна, которые из этого следуют.

**Пустой `catch`** — худшее, что можно сделать:

```java,wrong_behavior
try {
    save(data);
} catch (IOException e) {
}
```

Данные не сохранились, а программа продолжает работать как будто всё хорошо.
Никаких следов — ни в логе, ни на экране. Такие места ищут потом сутками.

**`catch (Exception e)`** ловит всё подряд, включая то, о чём вы не думали. Если
вы готовы обработать проблему с файлом — ловите `IOException`, а не всё вообще.

**Потеря причины.** Переводя исключение в другой вид, исходное нужно передать:

```java
try {
    return Files.readString(path);
} catch (IOException e) {
    throw new ConfigException("не прочитали настройки", e);
}
```

Второй аргумент — причина. В трассировке она появится под пометкой `Caused by`,
и путь до настоящего источника сохранится. Без неё вы получите «не прочитали
настройки» и никакого понятия, почему.

> **Получилось:** вы понимаете, что исключение прерывает выполнение и
> поднимается по стеку вызовов до первого обработчика. Умеете писать
> `try`/`catch`/`finally` и знаете, почему `return` в `finally` опасен.
> Различаете `Error`, `RuntimeException` и проверяемые исключения и понимаете,
> что каждая ветка означает. Умеете объявлять `throws` и своё исключение,
> знаете, почему узкий `catch` идёт раньше широкого. И, главное, знаете правило:
> ловить только то, с чем знаете, что делать, — а остальное пропускать наверх.
