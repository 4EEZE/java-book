# Виртуальные потоки

Вся прошлая глава исходила из того, что поток — дорогой ресурс, который надо
беречь. Из этого выросли пулы, очереди задач и целые библиотеки, посвящённые
тому, чтобы не создавать потоки лишний раз.

В Java 21 предпосылка изменилась.

## Почему поток был дорогим

Обычный поток Java — это поток операционной системы. У него есть стек
фиксированного размера, обычно около мегабайта, выделяемый заранее.
Переключение между такими потоками делает ядро системы, и стоит оно тысяч
процессорных тактов.

Отсюда всё остальное. Десять тысяч потоков — десять гигабайт под стеки, и
система умирает. Поэтому потоков заводят по числу ядер, складывают в пул и
переиспользуют.

Но для сервера это плохой компромисс. Сервер почти всё время **ждёт**: запроса к
базе, ответа сети, чтения файла. Поток, который ждёт, не делает ничего полезного
— он лишь занимает память и место в пуле. Тысяча одновременных пользователей
при пуле в двести потоков означает, что восемьсот ждут очереди, хотя процессор
простаивает.

Обходили это асинхронным программированием: не блокировать поток, а оставить
обработчик на потом. Работает, но код превращается в цепочку обратных вызовов,
трассировка теряет смысл, а отладка становится мучением.

## Виртуальный поток

**Виртуальный поток** — поток, которым управляет не операционная система, а сама
виртуальная машина. Стек у него растёт по мере надобности и живёт в куче,
переключение происходит без участия ядра.

Стоит он не мегабайты, а сотни байт.

```java
Thread.ofVirtual().start(() -> IO.println("из виртуального потока"));
```

Посмотрим, что это меняет. Запустим пятьдесят тысяч задач, каждая из которых
спит сто миллисекунд:

```java
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 50_000; i++) {
        pool.submit(() -> {
            Thread.sleep(Duration.ofMillis(100));
            return null;
        });
    }
}
```

```text
50000 виртуальных потоков со сном 100мс: 225 мс
```

Двести двадцать пять миллисекунд на пятьдесят тысяч потоков. Обычными потоками
эту программу запустить нельзя вовсе: пятьдесят тысяч стеков по мегабайту — это
пятьдесят гигабайт.

Обратите внимание на общее время: сто миллисекунд занял сам сон, остальное —
накладные расходы на пятьдесят тысяч потоков. То есть примерно ничего.

## Как это устроено

> **Под капотом:** виртуальных потоков много, а несущих их платформенных —
> по числу ядер. Фокус в том, что происходит при ожидании.
>
> Когда виртуальный поток вызывает что-то блокирующее — сон, чтение из сети,
> ожидание блокировки, — виртуальная машина **снимает** его с платформенного
> потока и сохраняет его стек в кучу. Платформенный поток тут же берёт другой
> виртуальный. Когда ожидание закончится, стек восстановят, возможно уже на
> другом платформенном потоке.
>
> Отсюда важное следствие: **виртуальные потоки не ускоряют вычисления**. Если
> задача считает, а не ждёт, она занимает платформенный поток целиком, и больше
> чем по числу ядер их параллельно не выполнится. Выигрыш появляется там, где
> потоки **ждут**, — то есть в серверах и в работе с сетью.

## Как ими пользоваться

Главное отличие от обычных потоков — их **не нужно переиспользовать**.

```java
// раньше: беречь потоки, складывая в пул
ExecutorService pool = Executors.newFixedThreadPool(200);

// теперь: поток на задачу
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Request request : requests) {
        pool.submit(() -> handle(request));
    }
}
```

`newVirtualThreadPerTaskExecutor` создаёт по виртуальному потоку на каждую
задачу — столько, сколько задач. Пул тут не хранилище потоков, а просто способ
дождаться завершения: `try` с ресурсами из главы 4 закрывает его, а закрытие
ждёт, пока всё выполнится.

Самое приятное — что писать код можно **прямо**, блокирующим стилем:

```java
String data = fetchFromNetwork(url);     // блокирует — и это нормально
int parsed = parse(data);
save(parsed);
```

Никаких обратных вызовов, обычная трассировка при ошибке, привычные
`try`/`catch`. То, ради чего раньше городили асинхронность, теперь получается
само.

## Что осталось прежним

Виртуальные потоки решают задачу количества, и только её. Всё из прошлой главы
остаётся в силе:

**Гонки никуда не делись.** Два виртуальных потока, увеличивающих общий счётчик,
теряют увеличения точно так же.

**`synchronized`, `volatile` и атомарные типы нужны так же.**

**Взаимная блокировка возможна так же.**

Более того, задача обостряется: раньше одновременных потоков было двести, теперь
их пятьдесят тысяч, и редкая гонка, которая прежде случалась раз в месяц, теперь
случится сегодня.

> **Современный подход:** если пишете новый сервер или что-то, что много ждёт, —
> берите виртуальные потоки и обычный блокирующий код. Это проще любой
> асинхронной схемы и даёт ту же пропускную способность.
>
> Две оговорки, о которые спотыкаются.
>
> **Не складывайте виртуальные потоки в пул фиксированного размера.** Это
> уничтожает всю идею: вы снова ограничиваете количество там, где ограничивать
> нечего. Виртуальный поток создаётся под задачу и умирает вместе с ней.
>
> **Осторожнее с `synchronized` вокруг долгого ожидания.** В ранних версиях
> виртуальный поток внутри `synchronized` не снимался с платформенного, и тот
> простаивал — это называли закреплением. В Java 24 ограничение сняли, но если
> работаете на 21 или 22, для долгих ожиданий лучше `ReentrantLock`.

## Структурированная многопоточность

Есть и вторая часть той же истории. Когда задача разбивается на подзадачи,
возникает вопрос: кто отвечает за их завершение, и что делать, если одна упала?

```java
try (var scope = StructuredTaskScope.open()) {
    var user = scope.fork(() -> loadUser(id));
    var orders = scope.fork(() -> loadOrders(id));

    scope.join();

    return new Profile(user.get(), orders.get());
}
```

Обе подзадачи идут параллельно, `join()` ждёт обе. Если одна падает — вторую
отменяют, и ошибка приходит наверх; если выход из блока происходит раньше —
отменяют всё.

Смысл в том, что время жизни подзадач ограничено блоком кода, ровно как время
жизни локальной переменной. Задачи не могут пережить создавший их метод и
остаться работать в никуда.

Одна существенная оговорка: в отличие от виртуальных потоков, которые давно
готовы, эта возможность **всё ещё предварительная**. Компилировать и запускать
её нужно с особым флагом:

```console
$ java --enable-preview --source 26 Main.java
```

```text
error: StructuredTaskScope is a preview API and is disabled by default.
  (use --enable-preview to enable preview APIs)
```

— вот что вы получите без флага. И, что важнее, её внешний вид менялся от
выпуска к выпуску: примеры из статей двухлетней давности уже не соберутся.
Сверяйтесь с документацией именно своей версии, а в рабочий код берите, только
понимая, что при обновлении Java его придётся править.

> **Получилось:** вы понимаете, почему обычный поток дорог и откуда взялись
> пулы. Знаете, что виртуальный поток управляется виртуальной машиной, стоит
> сотни байт и снимается с несущего потока на время ожидания. Понимаете, что
> ускорения вычислений они не дают, а дают возможность ждать одновременно
> десятками тысяч. Знаете, что создавать их нужно по одному на задачу, а не
> складывать в пул. И помните, что все опасности прошлой главы остались — и
> стали вероятнее.

Осталась одна теоретическая глава — про возможности, которые встречаются редко,
но встречаются.
