# Записи, запечатанные типы и сопоставление с образцом

Эта глава — про то, как в Java описывают данные. Три возможности, которые
появились за последние годы и вместе меняют стиль кода сильнее, чем каждая по
отдельности.

Мы четырежды обещали вернуться сюда: из [главы 4](ch04-00-references.md) — про неизменяемость, из главы 5
— про классы из одних полей, из [главы 6](ch06-00-interfaces.md) — про `instanceof` и про длинные цепочки
проверок типа. Пора.

## Класс из одних полей

Вспомним книгу из [главы 5](ch05-00-classes.md). Чтобы получить честный класс с двумя значениями,
пришлось написать примерно это:

```java
public class Book {
    private final String title;
    private final int year;

    public Book(String title, int year) {
        this.title = title;
        this.year = year;
    }

    public String getTitle() { return title; }
    public int getYear() { return year; }
}
```

И этого ещё мало. Чтобы две одинаковые книги считались равными, нужен `equals`;
чтобы книгу можно было положить в справочник — `hashCode`; чтобы её можно было
осмысленно напечатать — `toString`. Все три пишутся по шаблону и занимают ещё
строк тридцать.

Содержательной информации во всём этом — ровно одна строка: у книги есть
название и год. Остальное — обряд.

## Запись

**Запись** (`record`) описывает ровно то, что нужно:

<span class="filename">Файл: Book.java</span>

```java
public record Book(String title, int year) {}
```

Всё. Компилятор сам создаёт поля, конструктор, методы доступа, `equals`,
`hashCode` и `toString`.

Посмотрим на них на примере покороче:

<span class="filename">Файл: Point.java</span>

```java
public record Point(int x, int y) {}
```

```java
void main() {
    Point a = new Point(1, 2);
    Point b = new Point(1, 2);

    IO.println(a);
    IO.println(a.x() + " " + a.y());
    IO.println(a.equals(b));
    IO.println(a == b);
}
```

```text
Point[x=1, y=2]
1 2
true
false
```

Разберём вывод, в нём три важные вещи.

`toString` сразу осмысленный — имя записи и все поля. Для обычного класса
он напечатал бы что-то вроде `Point@1b6d3586`, то есть ничего.

Методы доступа называются `x()` и `y()`, а не `getX()` и `getY()`. Запись —
не старый класс с полями, и приставки `get` у неё нет; это осознанное решение
языка.

`equals` сравнивает **по содержимому**: две разные записи с одинаковыми полями
равны. При этом `==` по-прежнему отвечает `false`, потому что объекты разные —
всё ровно так, как мы разбирали в главе 4. Разница в том, что теперь `equals`
написан за вас и написан правильно.

`hashCode` тоже согласован с `equals` — что это значит и почему важно, разберём
в [главе 11](ch11-00-object-contracts.md).

## Проверка при создании

Запись — не просто набор полей: она может следить за собой. Для этого есть
**компактный конструктор**:

<span class="filename">Файл: Book.java</span>

```java
public record Book(String title, int year) {
    public Book {
        if (year < -3000 || year > 2100) {
            throw new IllegalArgumentException("Сомнительный год: " + year);
        }
        title = title.trim();
    }
}
```

```text
Book[title=Идиот, year=1869]
Exception in thread "main" java.lang.IllegalArgumentException: Сомнительный год: -5000
```

Обратите внимание на форму: у конструктора **нет списка параметров** и нет
присваиваний полям. Параметры те же, что у записи, а присвоит их компилятор сам
— после того, как отработает ваш код.

Поэтому строка `title = title.trim()` меняет не поле, а параметр, и в поле
попадает уже очищенное значение. Так записи нормализуют входные данные: обрезают
пробелы, приводят к нужному регистру, заменяют `null` на пустой список.

Проверка при создании — самая ценная часть. Раз объект неизменяем, проверить
его достаточно один раз: дальше он не испортится. Книга с сомнительным годом
просто не появится на свет.

## Записи неизменяемы

Поля записи всегда `final`:

```java,does_not_compile
Point p = new Point(1, 2);
p.x = 5;
```

```text
error: cannot assign a value to final variable x
```

Изменить запись нельзя — можно создать новую:

```java
Book corrected = new Book(book.title(), 1870);
```

Это не ограничение, а вся суть. Вспомните главу 4: неизменяемый объект нельзя
испортить из другого места программы, его безопасно передавать куда угодно и
читать из нескольких потоков без блокировок.

> **Современный подход:** записи стоит делать выбором по умолчанию для всего,
> что описывает данные, — точки, деньги, координаты, ответ сервера, строчка
> отчёта. Обычный класс берите тогда, когда у объекта есть **поведение** и
> изменяемое состояние: счёт, с которого снимают деньги, соединение, которое
> открывают и закрывают, игра, которая идёт.
>
> Простой признак: если вы ловите себя на написании геттеров ко всем полям —
> это запись. Если пишете методы, которые что-то делают, а не просто отдают
> значения, — это класс.

Запись не годится, когда нужно наследование (наследовать запись нельзя), когда
полям нужно меняться или когда часть данных не должна участвовать в сравнении.

## Запечатанные типы

Вторая возможность решает другую задачу. Иногда вариантов у типа ровно
несколько, и хочется сказать это вслух.

Обычный интерфейс так не умеет: реализовать его может кто угодно. **Запечатанный
интерфейс** перечисляет свои реализации:

<span class="filename">Файл: Shape.java</span>

```java
public sealed interface Shape permits Circle, Rect {}
```

<span class="filename">Файл: Circle.java</span>

```java
public record Circle(double radius) implements Shape {}
```

<span class="filename">Файл: Rect.java</span>

```java
public record Rect(double width, double height) implements Shape {}
```

Теперь фигура — это круг или прямоугольник, и третьего не дано. Попытка
реализовать `Shape` откуда-то ещё не скомпилируется.

Само по себе это звучит как ограничение. Ценность появляется, когда за дело
берётся `switch`.

## Сопоставление с образцом

`switch` умеет ветвиться по типу:

```java
String describe(Shape s) {
    return switch (s) {
        case Circle c -> "круг r=" + c.radius();
        case Rect r -> "прямоугольник " + r.width() + "×" + r.height();
    };
}
```

```text
круг r=1.0
прямоугольник 2.0×3.0
```

Заметьте, чего здесь нет: ветки `default`. И это не упущение.

Компилятор знает, что `Shape` — запечатанный тип и вариантов ровно два. Оба
покрыты, значит `switch` полон, и `default` не нужен. А если добавить третью
фигуру и забыть про неё здесь — программа перестанет компилироваться:

```java,does_not_compile
String d = switch (s) {
    case Circle c -> "круг";
};
```

```text
error: the switch expression does not cover all possible input values
```

Вот ради чего всё затевалось. Обычно добавление нового варианта — самая опасная
правка: где-то в коде остаётся `if`, который про него не знает, и программа
тихо делает не то. Здесь компилятор находит **все** такие места и отказывается
собирать программу, пока вы их не поправите.

Сравните с цепочкой `instanceof` из главы 6: там `default` или финальный `else`
проглотил бы новый вариант молча.

## Разбор записи на части

Образец умеет не только проверять тип, но и доставать содержимое:

```java
String describe(Shape s) {
    return switch (s) {
        case Rect(double w, double h) when w == h -> "квадрат " + w;
        case Rect(double w, double h) -> "прямоугольник " + w + "×" + h;
        case Circle(double r) -> "круг " + r;
    };
}
```

```text
квадрат 2.0
прямоугольник 2.0×3.0
```

`case Rect(double w, double h)` читается так: если это прямоугольник — возьми
его ширину в `w`, а высоту в `h`. Отдельно вызывать методы доступа не нужно.

`when w == h` — **страж**: дополнительное условие к образцу. Ветка срабатывает,
только когда прямоугольник оказался квадратом.

Порядок веток важен: они проверяются сверху вниз, поэтому более частный случай
должен идти раньше более общего. Поставьте их наоборот — и программа не
соберётся:

```text
error: this case label is dominated by a preceding case label
        case Rect(double w, double h) when w == h -> "квадрат " + w;
             ^
```

«Перекрыта предыдущей» — предыдущая ветка забирает все прямоугольники, и до
этой ничего не доходит. Ещё одна ошибка, которую в цепочке `if` пришлось бы
искать глазами.

Образцы вкладываются друг в друга:

```java
record Named(String name, Shape shape) {}

String label(Named n) {
    return switch (n) {
        case Named(String name, Circle(double r)) -> name + ": круг " + r;
        case Named(String name, Shape any) -> name + ": фигура";
    };
}
```

```text
мой: круг 5.0
```

Первая ветка срабатывает, только если внутри именованной фигуры действительно
круг, и сразу достаёт его радиус — с любой глубины вложенности, одной строкой.

## Зачем это всё вместе

Три возможности из этой главы — не три отдельных удобства. Вместе они дают
способ описывать данные, который в других языках называют алгебраическими
типами.

Идея простая. Есть данные, у которых **есть части**: у прямоугольника ширина и
высота. И есть данные, у которых есть **варианты**: фигура — это круг или
прямоугольник. Запись описывает первое, запечатанный тип — второе, а
сопоставление с образцом позволяет разбирать и то и другое, причём компилятор
следит за полнотой.

Практическая разница ощущается в правках. Добавляя вариант в запечатанный тип,
вы не ищете по коду места, которые надо обновить, — компилятор перечисляет их
сам. Это принципиально надёжнее, чем grep по проекту, и именно поэтому такой
стиль стоит применять, а не считать экзотикой.

> **Под капотом:** объектно-ориентированный подход и сопоставление с образцом
> решают одну задачу с разных сторон, и выбор между ними не вкусовой.
>
> При полиморфизме (глава 6) каждый класс сам знает, что ему делать: добавить
> **новый тип** легко — пишете класс, и ничего трогать не надо. А вот добавить
> **новую операцию** дорого: метод придётся дописать в каждый класс.
>
> С запечатанным типом и `switch` наоборот: новая операция — это один новый
> метод со `switch` внутри, а новый вариант требует правок во всех `switch`.
> Зато компилятор их перечислит.
>
> Правило выбора: если набор вариантов устоялся, а операции добавляются часто
> — запечатанный тип. Если операции известны, а типы добавляются — интерфейс и
> полиморфизм. Эту дилемму называют проблемой выражения, и универсального
> решения у неё нет.

## Итоги

Вы умеете описывать данные записью и знаете, что получаете
бесплатно, а что нет. Умеете проверять и нормализовать значения в компактном
конструкторе и понимаете, почему проверить неизменяемый объект достаточно
один раз. Знаете, что даёт запечатанный тип и почему `switch` по нему не
требует `default`. Умеете разбирать запись на части прямо в `case`,
пользоваться стражами и вкладывать образцы. И понимаете, когда выбирать этот
подход, а когда полиморфизм.

Дальше нам понадобится хранить много объектов сразу. Следующая глава — про
коллекции.
