# Продвинутые возможности

Последняя теоретическая глава — про то, что встречается реже, но встречается
обязательно. Перечисления, аннотации, рефлексия и вложенные классы.

## Перечисления

Когда у значения есть закрытый набор вариантов, его описывают перечислением:

<span class="filename">Файл: Status.java</span>

```java
public enum Status {
    NEW, IN_PROGRESS, DONE
}
```

Это не просто список констант. `Status` — полноценный тип: переменной такого
типа нельзя присвоить строку или число, а значит, опечатка невозможна. Сравните
с подходом «статус хранится строкой» — там `"DONE"` и `"Done"` разойдутся молча.

У перечисления могут быть поля, конструктор и методы:

```java
public enum Status {
    NEW("новый"),
    IN_PROGRESS("в работе"),
    DONE("готово");

    private final String label;

    Status(String label) {
        this.label = label;
    }

    public String label() {
        return label;
    }

    public boolean isFinal() {
        return this == DONE;
    }
}
```

```java
IO.println(Status.NEW + " / " + Status.NEW.label() + " / " + Status.NEW.ordinal());
IO.println(Arrays.toString(Status.values()));
IO.println(Status.valueOf("DONE").isFinal());
```

```text
NEW / новый / 0
[NEW, IN_PROGRESS, DONE]
true
```

Конструктор перечисления всегда закрытый: новые значения создать нельзя, их
ровно столько, сколько объявлено. `values()` даёт все варианты, `valueOf` ищет по
имени, `ordinal()` возвращает порядковый номер.

Про `valueOf` стоит помнить, что имя он требует точное, а на незнакомое отвечает
не `null`, а исключением `IllegalArgumentException`. Если имя приходит извне — из
файла, из запроса, — этот случай надо обработать.

Про `ordinal()` сразу предупреждение: не храните его в базе и не полагайтесь на
него. Добавите вариант в середину списка — все номера сдвинутся, а данные
останутся старыми. Храните имя.

Сравнивать значения перечисления через `==` можно и нужно — это тот редкий
случай, когда для объектов это правильно: экземпляр каждого варианта ровно один.

### `switch` по перечислению

```java
String action = switch (status) {
    case NEW -> "взять";
    case IN_PROGRESS -> "закончить";
    case DONE -> "закрыть";
};
```

```text
новый -> взять
в работе -> закончить
готово -> закрыть
```

Ветки `default` нет — и по той же причине, что в [главе 7](ch07-00-records-and-patterns.md): компилятор знает все
варианты и проверяет полноту. Добавите четвёртый статус — программа не соберётся,
пока вы не решите, что с ним делать.

Перечисление и запечатанный тип из главы 7 — про одно и то же, но с разных
сторон. Перечисление, когда вариантов конечное число и у них нет своих данных;
запечатанный тип, когда у каждого варианта своя структура.

Для коллекций из перечислений есть специальные реализации:

```java
IO.println(EnumSet.of(Status.NEW, Status.DONE));
Map<Status, Integer> counts = new EnumMap<>(Status.class);
```

```text
[NEW, DONE]
```

`EnumSet` и `EnumMap` внутри устроены на массивах и битовых масках — они быстрее
и компактнее обычных `HashSet` и `HashMap`. Если ключ перечисление, берите их.

## Аннотации

Аннотации мы уже встречали: `@Override` в [главе 6](ch06-00-interfaces.md), `@Test` в главе 12,
`@FunctionalInterface` в [главе 14](ch14-00-lambdas.md). Пора сказать, что это такое.

Аннотация — **помета на элементе кода**, которая сама по себе ничего не делает.
Смысл ей придаёт тот, кто её читает: компилятор, библиотека или ваш собственный
код.

Своя аннотация объявляется так:

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Command {
    String value();
}
```

`@interface` — объявление аннотации. `@Target` ограничивает, к чему её можно
приписать. `@Retention` — самое важное: до какого момента она доживает.

| Значение | Доживает до |
|---|---|
| `SOURCE` | только компиляции, в класс не попадает |
| `CLASS` | попадает в класс, но недоступна при работе |
| `RUNTIME` | доступна во время работы программы |

`@Override` имеет `SOURCE` — она нужна только компилятору. `@Test` имеет
`RUNTIME`, иначе JUnit не смог бы найти тесты.

## Рефлексия

Аннотация с `RUNTIME` бесполезна, если её некому прочитать. Читают её с помощью
**рефлексии** — способности программы рассматривать саму себя.

```java
var app = new Application();

for (Method method : Application.class.getDeclaredMethods()) {
    Command command = method.getAnnotation(Command.class);
    if (command != null) {
        IO.print(command.value() + " -> ");
        method.invoke(app);
    }
}
```

```text
привет -> здравствуйте
пока -> до свидания
```

Программа нашла свои же методы по помете и вызвала их, не зная имён заранее.
Именно так устроены JUnit, Spring и все библиотеки, которые «магическим образом»
что-то делают с вашими классами: никакой магии, только чтение аннотаций и вызов
по имени.

> **Современный подход:** рефлексия — инструмент для авторов библиотек, а не для
> прикладного кода. Причины конкретные.
>
> Она **обходит проверку типов**: `method.invoke(app)` компилятор проверить не
> может, и ошибка вылезет во время работы. Она **ломает рефакторинг**:
> переименуете метод — IDE не найдёт обращение по строке. Она **медленнее**
> обычного вызова. И она **обходит инкапсуляцию**, до которой мы дошли в главе
> 17: через `setAccessible(true)` можно добраться до приватного поля чужого
> класса.
>
> Если задача решается интерфейсом, перечислением или запечатанным типом из
> главы 7 — решайте ими. К рефлексии обращайтесь, когда действительно нужно
> работать с типами, неизвестными на момент компиляции: каркас, загрузчик
> модулей, сериализация.

## Вложенные классы

Класс можно объявить внутри другого, и видов таких классов четыре.

**Статический вложенный** — обычный класс, которому просто отвели место внутри
другого:

```java
public class Order {
    public static class Item {
        private final String name;
        // ...
    }
}
```

Создаётся как `new Order.Item(...)`. Годится, когда класс осмыслен только в
связке с внешним.

**Внутренний** (без `static`) — держит ссылку на объект внешнего класса и может
обращаться к его полям:

```java
public class Order {
    private final List<Item> items = new ArrayList<>();

    public class Summary {
        public int count() {
            return items.size();   // поле внешнего объекта
        }
    }
}
```

Создаётся только через объект: `order.new Summary()`.

> **Под капотом:** невидимая ссылка на внешний объект — причина, по которой
> внутренние классы рекомендуют использовать с осторожностью. Пока жив хотя бы
> один экземпляр внутреннего класса, внешний объект не может быть собран
> сборщиком мусора, даже если больше никому не нужен. Это утечка ровно того
> вида, что мы разбирали в [главе 4](ch04-00-references.md): ссылка живёт дольше, чем нужен объект.
>
> Правило простое: если внутреннему классу не нужны поля внешнего — пишите
> `static`. Это почти всегда так.

**Локальный** — объявленный внутри метода. Встречается редко.

**Анонимный** — класс без имени, созданный на месте; мы видели его в главе 14 как
предшественника лямбд. Сегодня для функциональных интерфейсов пишут лямбду, но
когда нужно реализовать интерфейс с несколькими методами разово, анонимный класс
остаётся уместным.

## Что мы не разобрали

Честно перечислим то, что в книгу не поместилось, чтобы вы знали, что оно
существует.

**Работа с датой и временем** — пакет `java.time`: `LocalDate`, `Instant`,
`Duration`, часовые пояса. Область большая и полная тонкостей.

**Сериализация** — превращение объектов в байты и обратно. Встроенный механизм
Java сегодня считается неудачным и небезопасным; на практике используют JSON
через библиотеки вроде Jackson.

**Регулярные выражения** — мы пользовались ими в [главе 13](ch13-00-cli-project.md), но не разбирали.

**Работа с сетью** поверх того, что мы напишем в следующей главе: `HttpClient`,
веб-каркасы, базы данных через JDBC.

Всё это лучше изучать по задаче, а не подряд. Основа, на которую это ложится, у
вас уже есть.

## Итоги

почему `switch` по нему проверяется на полноту, а `ordinal()` не стоит хранить.

её место в библиотеках, а не в прикладном коде. Различаете четыре вида
