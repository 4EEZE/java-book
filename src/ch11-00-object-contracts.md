# Контракты объектов: `equals`, `hashCode`, `toString`

Эта глава закрывает долги. В [главе 3](ch03-00-common-concepts.md) два `Integer` со значением 128 сравнились
через `==` не так, как ожидалось. В [главе 4](ch04-00-references.md) мы вывели правило «примитивы через
`==`, объекты через `equals`», не объяснив, откуда берётся `equals`. В [главе 8](ch08-00-collections.md)
объект потерялся внутри множества. В [главе 7](ch07-00-records-and-patterns.md) запись получила все эти методы
даром — но что именно она получила, мы не разбирали.

Разберём.

## Что объект умеет с рождения

Каждый класс в Java неявно наследует класс `Object`, и три его метода
достаются всем:

```java
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

void main() {
    Point a = new Point(1, 2);
    Point b = new Point(1, 2);

    IO.println(a);
    IO.println(a.equals(b));
    IO.println(a.equals(a));
}
```

```text
Main$Point@6591f517
false
true
```

`toString()` по умолчанию печатает имя класса и шестнадцатеричное число. Число —
не адрес в памяти, как часто думают, а результат `hashCode()`. Полезной
информации в такой строке ноль.

`equals()` по умолчанию сравнивает через `==`, то есть отвечает на вопрос «это
один и тот же объект?». Поэтому `a.equals(b)` — `false`: объекты разные. А
`a.equals(a)` — `true`.

Для `Point` такое поведение бесполезно. Две точки с одинаковыми координатами —
это одна и та же точка, и программа должна считать их равными.

## `equals`: контракт

Переопределим:

```java
@Override
public boolean equals(Object o) {
    return o instanceof Point p && p.x == x && p.y == y;
}
```

Разберём запись. Параметр обязан иметь тип `Object` — иначе это не
переопределение, а перегрузка, и коллекции им не воспользуются. Здесь и
пригождается `@Override` из [главы 6](ch06-00-interfaces.md): с ней ошибка обнаружится сразу.

`o instanceof Point p` — образец из главы 6: проверяет тип и сразу даёт
переменную нужного типа. Заодно он отсекает `null`: для `null` проверка типа
всегда ложна, поэтому отдельная проверка не нужна.

Метод `equals` обязан удовлетворять контракту. Это не пожелание: коллекции и
алгоритмы стандартной библиотеки на него **опираются**.

- **Рефлексивность.** `x.equals(x)` — всегда `true`.
- **Симметричность.** Если `x.equals(y)`, то и `y.equals(x)`.
- **Транзитивность.** Если `x.equals(y)` и `y.equals(z)`, то `x.equals(z)`.
- **Согласованность.** Пока объекты не менялись, ответ не меняется.
- **`null`.** `x.equals(null)` — всегда `false`, и никаких исключений.

Выглядит очевидно, но нарушить эти правила легче, чем кажется, — ниже увидим как.

## `hashCode`: почему его нельзя забывать

Вот самая частая ошибка в Java, и стоит разобрать её подробно.

```java,wrong_behavior
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override
    public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
}

void main() {
    Point a = new Point(1, 2);
    Point b = new Point(1, 2);

    IO.println("equals: " + a.equals(b));

    Set<Point> set = new HashSet<>();
    set.add(a);
    IO.println("contains(b): " + set.contains(b));

    set.add(b);
    IO.println("размер множества: " + set.size());
}
```

```text
equals: true
contains(b): false
размер множества: 2
```

Прочитайте это ещё раз. Объекты равны — множество само это подтвердит, если
спросить. Но `contains` их не находит, а `add` считает разными и хранит обе
копии. Множество без повторов содержит два одинаковых элемента.

Причина в устройстве `HashSet`, которое мы разбирали в главе 8. Поиск идёт не
перебором, а вычислением: сначала `hashCode()` указывает ячейку, и только внутри
неё сравниваются элементы. Мы переопределили `equals`, но не `hashCode` — а тот
по умолчанию у каждого объекта свой. Две равные точки получили разные хеши,
легли в разные ячейки и друг друга не видят. До `equals` дело вообще не дошло.

Отсюда **контракт `hashCode`**:

- Равные объекты **обязаны** иметь равные хеши.
- Неравные объекты могут иметь равные хеши — это допустимо и называется
  коллизией.
- Пока объект не менялся, его хеш не меняется.

Первое правило — главное, и следствие из него простое: **переопределяя
`equals`, всегда переопределяйте `hashCode`**. Всегда. Обратное тоже верно:
переопределять один без другого бессмысленно.

Чинится в одну строку:

```java
@Override
public int hashCode() {
    return Objects.hash(x, y);
}
```

```text
contains: true
размер: 1
```

`Objects.hash(...)` принимает поля и вычисляет из них хеш. Писать формулу
вручную не нужно.

Важно, чтобы в `hashCode` и `equals` участвовал **один и тот же набор полей**.
Взяли в `equals` три поля, а в `hashCode` два — контракт ещё соблюдается
(равные объекты дадут равные хеши), но коллизий станет больше и словарь
замедлится. Взяли наоборот — контракт нарушен, и всё сломается, как выше.

> **Под капотом:** а что будет, если написать `hashCode`, всегда возвращающий
> ноль? Как ни странно, это **корректно**: равные объекты дают равные хеши,
> контракт соблюдён, программа работает правильно.
>
> Сломается только скорость. Все объекты попадут в одну ячейку, и поиск из
> вычисления превратится в перебор: вместо мгновенного доступа получится проход
> по всему содержимому. `HashMap` с миллионом элементов станет работать как
> список.
>
> Отсюда видно, что `hashCode` отвечает за производительность, а `equals` — за
> правильность. Плохой `hashCode` замедляет, неверный — ломает.

## Ловушка: наследование ломает симметричность

Теперь про контракт, который нарушить проще всего.

```java,wrong_behavior
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override
    public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
}

class ColoredPoint extends Point {
    final String color;

    ColoredPoint(int x, int y, String color) {
        super(x, y);
        this.color = color;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof ColoredPoint c
            && c.x == x && c.y == y && c.color.equals(color);
    }
}

void main() {
    Point p = new Point(1, 2);
    ColoredPoint cp = new ColoredPoint(1, 2, "красный");

    IO.println("p.equals(cp): " + p.equals(cp));
    IO.println("cp.equals(p): " + cp.equals(p));
}
```

```text
p.equals(cp): true
cp.equals(p): false
```

Равенство перестало быть взаимным. `Point` видит в цветной точке обычную и
соглашается; `ColoredPoint` требует совпадения цвета и отказывается.

Последствия хуже, чем странный вывод. Список найдёт элемент или нет — в
зависимости от того, что вы ищете и что в нём лежит. Множество может содержать
обе точки или одну. Поведение зависит от порядка сравнения, а его вы не
контролируете.

Общего решения у этой задачи нет — она принципиальная. Есть два обхода.

**Первый: сравнивать классы точно.** Вместо `instanceof` использовать
`getClass() != o.getClass()`. Тогда обычная и цветная точки никогда не равны, и
симметричность восстанавливается. Взамен теряется возможность считать
равными объекты класса и его наследника, что иногда нужно.

**Второй, и обычно правильный: не наследовать классы с `equals`.** Вместо
наследования — композиция, как мы обсуждали в главе 6. Цветная точка не
наследует точку, а содержит её полем.

> **Современный подход:** всё, о чём эта глава, — работа, которую сегодня можно
> не делать. Запись из главы 7 получает `equals`, `hashCode` и `toString`
> готовыми, согласованными между собой и построенными по всем полям:
>
> ```java
> public record Point(int x, int y) {}
> ```
>
> Никакой возможности забыть `hashCode` или разойтись в наборе полей.
> Симметричность тоже не сломать: записи нельзя наследовать.
>
> Поэтому правило простое: для типов, которые описывают данные, пишите `record`.
> Руками эти три метода имеет смысл писать только в классах с поведением и
> изменяемым состоянием, где запись не подходит. А если всё же пишете —
> современные IDE генерируют их по набору полей, и генератору стоит доверять
> больше, чем себе.

## `equals` и `null`

Отдельная мелочь, которая экономит много времени:

```java,throws
String a = null;
IO.println(a.equals("текст"));
```

```text
Exception in thread "main" java.lang.NullPointerException
```

Вызывать `equals` у переменной, которая может быть `null`, опасно. Для этого
есть готовый метод:

```java
IO.println(Objects.equals(a, "текст"));
IO.println(Objects.equals(null, null));
```

```text
false
true
```

`Objects.equals(x, y)` сначала проверяет ссылки, потом `null`, и только потом
вызывает `equals`. Два `null` считаются равными, `null` и значение — нет.
Внутри собственного `equals` для полей ссылочного типа пользуйтесь именно им.

## `toString`

Третий метод контракта — самый простой и самый недооценённый.

```java
@Override
public String toString() {
    return "Point(" + x + ", " + y + ")";
}
```

`toString` вызывается неявно: при склейке со строкой, при печати, при выводе
коллекции, при показе объекта в отладчике и, что важнее всего, **в сообщениях
об ошибках**. Объект без `toString` в логе выглядит как `Main$Point@6591f517` —
и разбираться в аварии приходится вслепую.

Два правила. Включайте в строку поля, по которым объект узнают, — этого
достаточно. И не включайте пароли, токены и персональные данные: логи читают
многие, а `toString` вызывается там, где вы этого не ждёте.

## Итоги

Вы знаете, что `equals` и `toString` достаются от `Object` и
что они делают по умолчанию. Помните контракт `equals` — рефлексивность,
симметричность, транзитивность, согласованность, отношение к `null`. Знаете
контракт `hashCode` и главное правило: переопределяя `equals`, всегда
переопределяйте `hashCode`, иначе объект потеряется внутри множества.
Понимаете, почему `hashCode`, возвращающий ноль, корректен, но губителен для
скорости. Видели, как наследование ломает симметричность, и знаете два обхода.
И знаете, что всего этого можно не делать, если взять запись.

Мы разобрались, как объект отвечает за себя. Следующая глава — про то, как
проверить, что программа делает то, что обещает.
