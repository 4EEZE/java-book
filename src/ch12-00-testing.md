# Тестирование

До сих пор мы проверяли программы, запуская их и глядя на вывод. Для примера в
десять строк это работает. Для программы, которую правят месяцами, — нет:
проверять руками всё, что могло сломаться, никто не станет, а значит, никто и не
проверит.

Тест — это программа, которая запускает вашу программу и проверяет результат.
Написанная один раз, она выполняется за миллисекунды и столько раз, сколько
нужно.

## Что будем проверять

Возьмём класс денег. Помните правило из [главы 3](ch03-00-common-concepts.md) — деньги не считают в `double`?
Считаем в копейках:

<span class="filename">Файл: src/main/java/Money.java</span>

```java
public record Money(long kopecks) {
    public Money {
        if (kopecks < 0) {
            throw new IllegalArgumentException("отрицательная сумма: " + kopecks);
        }
    }

    public Money plus(Money other) {
        return new Money(kopecks + other.kopecks);
    }

    public Money times(int factor) {
        return new Money(kopecks * factor);
    }

    @Override
    public String toString() {
        return kopecks / 100 + "," + String.format("%02d", kopecks % 100);
    }
}
```

Запись из [главы 7](ch07-00-records-and-patterns.md) с проверкой в компактном конструкторе и своим `toString` —
зачем он, станет видно через минуту.

## Первый тест

Тесты пишут с помощью библиотеки. Стандарт в Java — **JUnit**; добавим его в
`pom.xml`:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.3</version>
    <scope>test</scope>
</dependency>
```

`<scope>test</scope>` означает, что библиотека нужна только при тестировании и в
итоговый JAR не попадёт.

Тесты живут в `src/test/java` — том самом каталоге из [главы 1](ch01-00-getting-started.md):

<span class="filename">Файл: src/test/java/MoneyTest.java</span>

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class MoneyTest {

    @Test
    void сложение_складывает_копейки() {
        Money result = new Money(100).plus(new Money(200));
        assertEquals(new Money(300), result);
    }
}
```

```console
$ mvn test
```

```text
Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
```

Разберём, что здесь есть.

`@Test` — аннотация, помечающая метод как тест. Без неё JUnit метод не заметит.

`assertEquals(ожидаемое, полученное)` — **утверждение**. Если значения равны,
тест проходит молча; если нет — падает. Порядок аргументов важен для сообщения
об ошибке: сначала то, что вы ожидали.

`import static` — статический импорт: он позволяет писать `assertEquals`, а не
`Assertions.assertEquals`. Для тестов это общепринято.

Заметьте, что тест сравнивает объекты через `assertEquals` — а тот внутри
вызывает `equals`. Если бы `Money` был обычным классом без `equals` из [главы 11](ch11-00-object-contracts.md),
тест падал бы всегда, сколько бы копеек мы ни считали. Запись даёт `equals`
даром, и тест сразу работает.

## Как читать падение

Сломаем тест нарочно — так понятнее:

```java
@Test
void этот_тест_падает() {
    assertEquals(new Money(999), new Money(100).plus(new Money(200)));
}
```

```text
MoneyTest > этот_тест_падает() ✘ expected: <9,99> but was: <3,00>
```

Вот зачем нужен `toString` из главы 11. Сообщение показывает суммы в читаемом
виде — `9,99` и `3,00`. Без `toString` там было бы `Money@6591f517` и
`Money@70beb599`, и понять, что произошло, стало бы невозможно.

Хороший `toString` окупается именно здесь: его почти не читают в обычной работе
программы, зато читают каждый раз, когда что-то сломалось.

## Набор утверждений

Их немного, и больше обычно не нужно:

```java
@Test
void основные_утверждения() {
    assertEquals(new Money(300), new Money(100).plus(new Money(200)));
    assertNotEquals(new Money(1), new Money(2));

    assertTrue(new Money(300).kopecks() > 0);
    assertFalse(new Money(0).kopecks() > 0);

    assertNull(null);
    assertNotNull(new Money(1));
}
```

Отдельно стоит `assertThrows` — он проверяет, что код **падает**, и падает как
надо:

```java
@Test
void отрицательная_сумма_отвергается() {
    var error = assertThrows(
        IllegalArgumentException.class,
        () -> new Money(-1)
    );
    assertTrue(error.getMessage().contains("-1"));
}
```

`() -> new Money(-1)` — лямбда из [главы 14](ch14-00-lambdas.md); пока читайте это как «вот код,
который надо попробовать выполнить». `assertThrows` запускает его, убеждается,
что вылетело исключение нужного типа, и возвращает это исключение — чтобы можно
было проверить и сообщение.

Проверять исключения не менее важно, чем удачные случаи. Компактный конструктор
из главы 7 отвергает отрицательные суммы — но если однажды кто-то уберёт
проверку, сломается именно этот тест, а не что-то далёкое.

## Как называть тесты

Имя теста — это не имя метода, а фраза, которую вы прочтёте в отчёте о падении.
Поэтому здесь нарушают обычные соглашения Java об именах:

```java
@Test
void сложение_складывает_копейки() { }
```

Подчёркивания вместо `camelCase`, и имя описывает **поведение**, а не метод.
Плохое имя: `testPlus`. Хорошее: `сложение_складывает_копейки`. Первое сообщает,
что сломался `plus`; второе — что именно он перестал делать.

Если название неудобно писать словами, JUnit позволяет задать его отдельно:

```java
@Test
@DisplayName("сложение складывает копейки")
void additionAddsKopecks() { }
```

## Из чего состоит тест

У хорошего теста три части, и разделять их полезно даже пустой строкой:

```java
@Test
void умножение_повторяет_сумму() {
    Money price = new Money(100);       // подготовка

    Money total = price.times(5);       // действие

    assertEquals(new Money(500), total); // проверка
}
```

**Подготовка** — создаём то, с чем работаем. **Действие** — вызываем ровно то,
что проверяем, одной строкой. **Проверка** — сравниваем результат с ожидаемым.

Если действие не помещается в одну строку или проверок набирается пять, это
обычно значит, что тест проверяет слишком много сразу. Один тест — одно
утверждение о поведении.

## Общая подготовка

Когда несколько тестов начинаются одинаково, повторение выносят:

```java
class MoneyTest {
    private Money hundred;

    @BeforeEach
    void подготовка() {
        hundred = new Money(100);
    }

    @Test
    void сложение() {
        assertEquals(new Money(300), hundred.plus(new Money(200)));
    }

    @Test
    void умножение() {
        assertEquals(new Money(500), hundred.times(5));
    }
}
```

`@BeforeEach` выполняется **перед каждым** тестом, а не один раз на класс. Это
важно: каждый тест получает свежий объект и не зависит от того, что натворили
предыдущие.

Тесты обязаны быть независимыми. Тест, который проходит только после другого
теста, — это не тест, а ловушка: однажды порядок изменится, и вы получите
загадочное падение.

## Один тест, много данных

Когда проверяется одно и то же поведение на разных значениях, копировать тест не
нужно:

```java
@ParameterizedTest
@ValueSource(longs = {0, 1, 100, 999_999})
void любая_неотрицательная_сумма_принимается(long kopecks) {
    assertEquals(kopecks, new Money(kopecks).kopecks());
}
```

JUnit запустит метод четыре раза и покажет в отчёте каждый случай отдельно —
поэтому при падении сразу видно, на каком значении.

## Что тестировать, а что нет

> **Современный подход:** покрытие тестами измеряют в процентах, и это число
> легко превратить в самоцель. Цель не в проценте.
>
> Тестировать стоит **поведение, а не устройство**. Тест, который проверяет,
> что метод возвращает правильную сумму, переживёт переписывание этого метода.
> Тест, который проверяет, что внутри вызвался определённый метод в определённом
> порядке, сломается при первом же рефакторинге — хотя программа осталась
> правильной. Такие тесты хуже, чем их отсутствие: они не ловят ошибки, но
> мешают менять код.
>
> В первую очередь пишите тесты на: логику с ветвлениями и вычислениями;
> граничные случаи — ноль, пустая строка, пустая коллекция, максимальное
> значение; и на каждую найденную ошибку. Последнее особенно ценно: тест,
> написанный по следам ошибки, гарантирует, что она не вернётся.
>
> Не стоит тестировать: геттеры и сеттеры, конструкторы без логики, чужие
> библиотеки. Они либо не могут сломаться, либо не ваша ответственность.

## Тест как описание поведения

Есть подход, при котором тест пишут **до** кода: сначала формулируют, чего от
программы хотят, убеждаются, что тест падает, и только потом пишут код, пока он
не пройдёт. Называется это разработкой через тестирование.

Спорить о том, всегда ли так надо делать, здесь не будем. Но одно наблюдение
полезно независимо от подхода: если тест на код написать трудно, обычно дело не
в тесте, а в коде. Метод, которому для проверки нужны база, сеть и настройки,
скорее всего, делает слишком много и просится на разделение.

## Итоги

Вы умеете написать тест с `@Test` и утверждениями, проверить
исключение через `assertThrows`, вынести общую подготовку в `@BeforeEach` и
прогнать один тест на многих данных. Знаете, из каких трёх частей состоит тест
и почему тесты обязаны быть независимыми. Понимаете, почему хороший `toString`
из главы 11 окупается именно в отчёте о падении. И знаете, что тестировать
стоит поведение, а не устройство.

Мы прошли достаточно, чтобы написать что-то целиком. Следующая глава —
проектная: программа командной строки.
