# Обобщённые типы

Угловые скобки встречались нам уже трижды: `List<String>` в [главе 8](ch08-00-collections.md),
`Comparable<Book>` в [главе 6](ch06-00-interfaces.md), `Map<String, Integer>` там же. Каждый раз мы
говорили «подробности в главе 10». Пришли.

## Задача

Напишем ящик, который хранит одно значение. Без обобщённых типов есть два
способа, и оба плохи.

Способ первый — по ящику на каждый тип:

```java
class StringBox {
    private final String value;
    // ...
}

class IntBox {
    private final int value;
    // ...
}
```

Код одинаковый с точностью до типа. Понадобился ящик для книги — пишем третий.

Способ второй — хранить `Object`, раз от него наследуется всё:

```java,throws
class Box {
    private final Object value;

    Box(Object value) { this.value = value; }
    Object get() { return value; }
}

void main() {
    Box box = new Box("текст");
    String s = (String) box.get();

    Box other = new Box(42);
    String wrong = (String) other.get();
}
```

```text
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer
cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String
are in module java.base of loader 'bootstrap')
```

(Сообщение приведено целиком, с переносами для читаемости — в консоли оно
одной строкой. Хвост про модуль и загрузчик здесь шум; смысл в первой половине.)

Ящик один, но теперь при каждом чтении нужно приведение типа, а компилятор
ничем не помогает: он не знает, что внутри. Положили число, прочитали как
строку — узнаете об этом во время работы программы.

Именно так коллекции в Java и работали до версии 5. Приведения были в каждой
второй строке, а `ClassCastException` — обычным делом.

## Обобщённый класс

Обобщённый тип позволяет сказать: ящик хранит что-то одно, а что именно —
решает тот, кто им пользуется.

<span class="filename">Файл: Box.java</span>

```java
public class Box<T> {
    private final T value;

    public Box(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}
```

```java
Box<String> text = new Box<>("текст");
Box<Integer> number = new Box<>(42);

IO.println(text.get().length() + " " + (number.get() + 1));
```

```text
5 43
```

`<T>` после имени класса объявляет **параметр типа**. Внутри класса `T`
используется как обычный тип: поле, параметр конструктора, результат метода.

`Box<String>` означает «ящик, у которого `T` — это `String`». Метод `get()`
возвращает уже `String`, а не `Object`, поэтому `.length()` вызывается прямо, без
приведения. И положить в такой ящик число не получится — компилятор не даст.

Буква `T` — просто соглашение (от *type*). Встречаются также `E` для элемента
коллекции, `K` и `V` для ключа и значения. Никакого особого смысла у этих букв
нет, но отступать от них не стоит: читатель к ним привык.

## Обобщённый метод

Параметр типа может принадлежать не классу, а отдельному методу:

```java
<E> E first(List<E> list) {
    return list.get(0);
}
```

```java
IO.println(first(List.of("а", "б")));
```

```text
а
```

`<E>` перед типом результата объявляет параметр типа для этого метода.
Указывать его при вызове не нужно — компилятор выводит `E` из аргумента.

Возвращается именно `String`, а не `Object`: обобщённый метод сохраняет тип
сквозь себя. Это главное, ради чего он нужен.

## Ограничения

Пока `T` — это «что угодно», с ним почти ничего нельзя сделать: компилятор
знает о нём только то, что он объект. Чтобы сравнивать значения, нужно
потребовать от типа способность сравниваться:

```java
<T extends Comparable<T>> T max(List<T> items) {
    T best = items.get(0);
    for (T item : items) {
        if (item.compareTo(best) > 0) {
            best = item;
        }
    }
    return best;
}
```

```java
IO.println(max(List.of(3, 7, 5)));
IO.println(max(List.of("б", "я", "а")));
```

```text
7
я
```

`<T extends Comparable<T>>` читается так: `T` — любой тип, который умеет
сравниваться сам с собой. Теперь `item.compareTo(best)` законен, потому что
компилятор знает: у `T` есть такой метод.

Обратите внимание, что `extends` здесь означает не наследование класса, а
«удовлетворяет». Для интерфейсов пишут тоже `extends`, а не `implements` — такая
у обобщённых типов грамматика.

## Стирание типов

А теперь главное, что отличает обобщённые типы в Java от почти всех остальных
языков.

```java
List<String> strings = new ArrayList<>();
List<Integer> numbers = new ArrayList<>();

IO.println(strings.getClass() == numbers.getClass());
IO.println(strings.getClass().getName());
```

```text
true
java.util.ArrayList
```

Это не опечатка. Во время работы программы `List<String>` и `List<Integer>` —
**один и тот же** тип. Угловые скобки существуют только для компилятора: он
проверяет по ним типы, расставляет нужные приведения и после этого **стирает**
информацию о параметре.

Называется это **стиранием типов**, и сделано было ради совместимости: когда
обобщённые типы добавляли в Java 5, требовалось, чтобы уже скомпилированный код
продолжал работать, а новый и старый — сочетаться. Стирание это обеспечило
ценой того, что во время работы программы параметр типа недоступен.

> **Под капотом:** сравните с C#, где обобщённые типы добавили примерно тогда же,
> но иначе: там `List<int>` и `List<string>` — действительно разные типы во время
> работы программы, и параметр можно спросить. Ценой стала несовместимость с
> предыдущей версией среды.
>
> Java выбрала совместимость. Оценки этого решения расходятся до сих пор, но
> практический вывод однозначен: обобщённые типы в Java — инструмент **времени
> компиляции**. Все проверки происходят до запуска, и это, если подумать,
> неплохо: ошибка, найденная компилятором, лучше ошибки, найденной
> пользователем.

## Что стирание запрещает

Из стирания следуют ограничения, о которые вы обязательно споткнётесь.

**Нельзя создать массив параметра типа:**

```java,does_not_compile
class Box<T> {
    T[] make() {
        return new T[10];
    }
}
```

```text
error: generic array creation
        return new T[10];
               ^
```

Массив во время работы программы знает тип своих элементов и проверяет его при
записи. А `T` к этому моменту стёрт, и проверять нечего. Вместо массива берут
`List<T>`.

**Нельзя проверить параметр типа:**

```java,does_not_compile
Object o = new ArrayList<String>();
IO.println(o instanceof List<String>);
```

```text
error: Object cannot be safely cast to List<String>
```

Проверить, что это список, можно — `o instanceof List<?>`. А что список именно
строк — нельзя: этой информации во время работы программы уже нет.

## Почему `List<String>` — не `List<Object>`

Вот место, которое удивляет практически всех.

```java,does_not_compile
List<Integer> numbers = List.of(1, 2, 3);
IO.println(sum(numbers));

double sum(List<Number> items) {
    double total = 0;
    for (Number n : items) {
        total += n.doubleValue();
    }
    return total;
}
```

```text
error: method sum in class Main cannot be applied to given types;
  required: List<Number>
  found:    List<Integer>
```

Каждое `Integer` — это `Number`, а список целых — **не** список чисел. Выглядит
как придирка, но она обоснована.

Представим, что было бы можно:

```java
List<Integer> numbers = new ArrayList<>();
List<Number> asNumbers = numbers;   // если бы это разрешили...
asNumbers.add(3.14);                // ...то сюда легло бы дробное число
int broken = numbers.get(0);        // ...и здесь бы всё рухнуло
```

Список целых содержал бы дробное число, а объявленный тип обещал обратное.
Компилятор запрещает первую строку, чтобы не допустить третью.

Такое свойство называют **инвариантностью**: `List<A>` не родственник
`List<B>`, даже если `A` — родственник `B`.

## Массивы устроены иначе, и это ошибка

Для массивов то же самое **разрешено**, и вот к чему это приводит:

```java,throws
String[] strings = new String[2];
Object[] objects = strings;
objects[0] = 42;
```

```text
Exception in thread "main" java.lang.ArrayStoreException: java.lang.Integer
```

Массив строк присвоился массиву объектов — компилятор не возразил. А при записи
числа в массив, который на самом деле строковый, программа упала.

Сравните два случая. С обобщёнными типами ошибка обнаружена **при компиляции**,
и программа просто не собралась. С массивами она обнаружена **во время работы**,
у пользователя.

Массивы в Java **ковариантны** — `String[]` считается разновидностью
`Object[]`, — и это признанная ошибка проектирования, оставшаяся с самой первой
версии языка. Обобщённые типы её сознательно не повторили.

## Подстановочные типы

Инвариантность правильна, но неудобна: метод `sum` выше честно не собирается
менять список, а принять список целых всё равно не может.

Для этого есть **подстановочный тип** — вопросительный знак:

```java
double sum(List<? extends Number> items) {
    double total = 0;
    for (Number n : items) {
        total += n.doubleValue();
    }
    return total;
}
```

```java
List<Integer> numbers = List.of(1, 2, 3);
IO.println(sum(numbers));
IO.println(sum(List.of(1.5, 2.5)));
```

```text
6.0
4.0
```

`List<? extends Number>` означает «список чего-то, что является числом, — а чего
именно, неважно». Теперь метод принимает и целые, и дробные.

Взамен появляется запрет: в такой список **нельзя добавлять**.

```java,does_not_compile
List<? extends Number> items = new ArrayList<Integer>();
items.add(1);
```

```text
error: no suitable method found for add(int)
```

И это правильно. Компилятор знает, что там числа, но не знает, какие именно: под
`? extends Number` может скрываться `List<Double>`, и целое число туда класть
нельзя. Раз безопасное добавление невозможно, запрещено любое.

Зеркальный случай — когда в список только добавляют:

```java
void fill(List<? super Integer> target) {
    target.add(1);
    target.add(2);
}
```

```java
List<Number> target = new ArrayList<>();
fill(target);
IO.println(target);
```

```text
[1, 2]
```

`? super Integer` означает «список чего-то, что является предком `Integer` или
им самим». Добавлять целые туда безопасно: любой такой список их примет. А вот
читать из него получится только `Object` — какой конкретно тип там, неизвестно.

> **Современный подход:** правило выбора запомнить проще, чем вывести. Оно
> называется PECS — *producer extends, consumer super*:
>
> - коллекция, из которой вы **читаете**, — `? extends T`;
> - коллекция, в которую вы **записываете**, — `? super T`;
> - делаете и то и другое — никаких подстановок, просто `T`.
>
> И практическое дополнение: подстановочные типы нужны в **параметрах методов**,
> которые вы пишете для чужого использования. В локальных переменных и в
> возвращаемых значениях они почти всегда лишние и только усложняют чтение.
> Если вы пишете обычный прикладной код и не встречаете `?`, это нормально.

## Итоги

Вы понимаете, зачем нужны обобщённые типы и что было до них.
Умеете объявлять обобщённый класс и обобщённый метод, ограничивать параметр
через `extends`. Знаете, что такое стирание типов, почему его выбрали и что
из-за него запрещено: массив параметра типа и проверка параметра через
`instanceof`. Понимаете, почему `List<Integer>` не подходит вместо
`List<Number>`, и почему у массивов это разрешено напрасно. Умеете применять
`? extends` и `? super` по правилу PECS.

Обобщённые типы позволили описать «контейнер чего-то». Следующая глава — про
то, что обязан уметь сам объект, чтобы его можно было сравнивать, складывать в
множество и осмысленно печатать.
