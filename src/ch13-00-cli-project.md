# Проект: программа командной строки

Соберём что-нибудь целиком. Программа будет читать текстовый файл и печатать
самые частые слова:

```console
$ java WordCount.java text.txt 3
3	на
2	кот
1	кота
```

По дороге пригодится почти всё из предыдущих глав: коллекции, записи,
исключения, тесты. Новыми будут три вещи — аргументы командной строки, чтение
файла и сортировка по нескольким признакам.

## Аргументы командной строки

До сих пор наш `main` не принимал ничего. Пора это исправить:

```java
void main(String[] args) {
    IO.println("получено аргументов: " + args.length);
    for (String arg : args) {
        IO.println("  " + arg);
    }
}
```

```console
$ java WordCount.java text.txt 3
получено аргументов: 2
  text.txt
  3
```

`args` — массив строк, всё, что написано после имени программы. Имени самой
программы в нём **нет**: в отличие от C, нулевой элемент — это первый аргумент.

Первым делом проверим, что нам вообще что-то передали:

```java
void main(String[] args) {
    if (args.length == 0) {
        IO.println("Использование: wordcount <файл> [сколько]");
        System.exit(2);
    }

    Path path = Path.of(args[0]);
    int limit = args.length > 1 ? Integer.parseInt(args[1]) : 5;
}
```

`System.exit(код)` немедленно завершает программу с указанным кодом возврата.
Ноль означает успех, всё остальное — ошибку; это соглашение операционной
системы, и на него опираются скрипты. Традиционно `2` означает «неправильно
вызвали», `1` — «не смогли сделать».

Второй аргумент необязателен: если его нет, берём пять. Обратите внимание, что
проверка `args.length > 1` **обязана** идти раньше обращения к `args[1]`, иначе
получим выход за границу массива.

## Чтение файла

```java
String text = Files.readString(path);
```

Одна строка — файл целиком в памяти. Для текста, который заведомо помещается,
этого достаточно; про чтение больших файлов по частям будет глава 16.

`Files.readString` бросает проверяемое `IOException` из главы 9, и компилятор не
даст его проигнорировать. Обработаем по-разному два случая:

```java
String text;
try {
    text = Files.readString(path);
} catch (NoSuchFileException e) {
    IO.println("Файл не найден: " + path);
    System.exit(1);
    return;
} catch (IOException e) {
    IO.println("Не удалось прочитать " + path + ": " + e.getMessage());
    System.exit(1);
    return;
}
```

Здесь виден принцип из главы 9: ловим то, с чем знаем что делать. «Файла нет» —
самая частая ошибка пользователя, и про неё стоит сказать понятно. Остальные
беды с вводом-выводом редки, и для них хватит сообщения от самой системы.

`NoSuchFileException` — наследник `IOException`, поэтому идёт первым: узкий тип
раньше широкого, иначе компилятор возразит.

`return` после `System.exit` может показаться лишним — программа ведь уже
завершилась. Но компилятор об этом не знает и считает, что `text` может остаться
без значения; это определённое присваивание из главы 3.

## Считаем слова

```java
Map<String, Integer> counts = new HashMap<>();
for (String word : text.toLowerCase().split("[^\\p{L}]+")) {
    if (!word.isEmpty()) {
        counts.merge(word, 1, Integer::sum);
    }
}
```

`split` разрезает строку по разделителю, заданному **регулярным выражением**.
`\p{L}` означает «любая буква любого алфавита», а `[^...]` — отрицание, то есть
«всё, что не буква». Плюс означает «одно или больше подряд».

Такой разделитель отсекает пробелы, точки, запятые и переводы строк разом, и
работает для кириллицы так же, как для латиницы. Простое деление по пробелу
оставило бы слова со знаками препинания: `окне.` и `окне` считались бы разными.

Проверка на пустоту нужна из-за края: если текст начинается с небуквы,
`split` вернёт пустую первую строку.

`merge(word, 1, Integer::sum)` — приём из главы 8: положить единицу, если слова
ещё не было, иначе прибавить к тому, что есть.

## Сортируем

Словарь порядка не обещает — это мы разбирали в главе 8. Чтобы получить самые
частые слова, содержимое надо переложить в список и отсортировать.

Заведём для пары «слово и счётчик» запись:

```java
record Entry(String word, int count) {}
```

```java
List<Entry> entries = new ArrayList<>();
counts.forEach((word, count) -> entries.add(new Entry(word, count)));

entries.sort(Comparator.comparingInt(Entry::count).reversed()
                       .thenComparing(Entry::word));
```

Сортировка — самая плотная строка в программе, разберём её по частям.

`Comparator.comparingInt(Entry::count)` создаёт сравнение по полю `count`.
`Entry::count` — ссылка на метод, то есть «функция, которая у записи берёт
счётчик»; подробно про такую запись — глава 14.

`.reversed()` переворачивает порядок: нам нужны частые сверху.

`.thenComparing(Entry::word)` задаёт, что делать при равенстве счётчиков —
сравнивать по слову. Без этого слова с одинаковой частотой шли бы в
непредсказуемом порядке, и вывод менялся бы от запуска к запуску.

Последнее стоит подчеркнуть: **устойчивый порядок вывода важен**. Программа,
которая на одних и тех же данных печатает разное, неудобна и почти непроверяема
тестами.

Осталось обрезать до нужного количества:

```java
return entries.subList(0, Math.min(limit, entries.size()));
```

`Math.min` защищает от случая, когда разных слов меньше, чем просили: без него
получили бы выход за границу.

## Программа целиком

<span class="filename">Файл: WordCount.java</span>

```java
import java.io.IOException;
import java.nio.file.*;
import java.util.*;

record Entry(String word, int count) {}

void main(String[] args) {
    if (args.length == 0) {
        IO.println("Использование: wordcount <файл> [сколько]");
        System.exit(2);
    }

    Path path = Path.of(args[0]);
    int limit = args.length > 1 ? Integer.parseInt(args[1]) : 5;

    String text;
    try {
        text = Files.readString(path);
    } catch (NoSuchFileException e) {
        IO.println("Файл не найден: " + path);
        System.exit(1);
        return;
    } catch (IOException e) {
        IO.println("Не удалось прочитать " + path + ": " + e.getMessage());
        System.exit(1);
        return;
    }

    for (Entry entry : topWords(text, limit)) {
        IO.println(entry.count() + "\t" + entry.word());
    }
}

List<Entry> topWords(String text, int limit) {
    Map<String, Integer> counts = new HashMap<>();
    for (String word : text.toLowerCase().split("[^\\p{L}]+")) {
        if (!word.isEmpty()) {
            counts.merge(word, 1, Integer::sum);
        }
    }

    List<Entry> entries = new ArrayList<>();
    counts.forEach((word, count) -> entries.add(new Entry(word, count)));
    entries.sort(Comparator.comparingInt(Entry::count).reversed()
                           .thenComparing(Entry::word));

    return entries.subList(0, Math.min(limit, entries.size()));
}
```

Проверим все три сценария:

```console
$ java WordCount.java text.txt 3
3	на
2	кот
1	кота

$ java WordCount.java
Использование: wordcount <файл> [сколько]

$ java WordCount.java нет.txt
Файл не найден: нет.txt
```

## Почему подсчёт вынесен в отдельный метод

Обратите внимание на устройство: `main` занимается вводом-выводом и завершением
программы, а `topWords` — только вычислением. Он принимает строку, возвращает
список и ничего не печатает.

Это сделано ради тестов. Метод, который читает файл, печатает на экран и
завершает программу, проверить почти невозможно. Метод, который из строки делает
список, проверяется в три строки.

Одна оговорка про форму записи. Всё, что мы писали выше, — компактный файл, и
именно его тестом со стороны **не достать**: неявный класс, который достраивает
компилятор, не имеет имени, и обратиться к его методам из другого файла нельзя.
Поэтому перед написанием тестов код переносят в обычный класс, как мы делаем с
главы 5:

```java
public class WordCount {
    public record Entry(String word, int count) {}

    public static List<Entry> topWords(String text, int limit) {
        // ...
    }

    public static void main(String[] args) {
        // ...
    }
}
```

Компактная форма хороша, пока программа помещается в один файл и запускается
одной командой. Как только появляются тесты, она своё отслужила.

```java
@Test
void считает_частоту_без_учёта_регистра() {
    List<Entry> top = topWords("Кот кот КОТ пёс", 2);

    assertEquals(new Entry("кот", 3), top.get(0));
    assertEquals(new Entry("пёс", 1), top.get(1));
}

@Test
void при_равной_частоте_сортирует_по_алфавиту() {
    List<Entry> top = topWords("бы аз", 2);

    assertEquals("аз", top.get(0).word());
    assertEquals("бы", top.get(1).word());
}

@Test
void просит_больше_чем_есть() {
    assertEquals(1, topWords("кот", 100).size());
}
```

Заметьте, что `assertEquals` сравнивает записи целиком — работает это потому,
что запись получила `equals` даром, как мы разбирали в главах 7 и 11.

Это общее правило, и оно стоит больше, чем кажется: **отделяйте вычисление от
ввода-вывода**. Вычисление тестируется, ввод-вывод — нет. Чем больше программы
попадает в первую часть, тем спокойнее её менять.

> **Современный подход:** разбор аргументов мы написали руками, и для двух
> аргументов это правильно. Как только появятся флаги вида `--limit 10`,
> `--ignore-case`, короткие псевдонимы и `--help`, писать это самому перестаёт
> окупаться: получится много кода, который делает то же, что и все.
>
> Для таких случаев берут готовую библиотеку — например, picocli: она описывает
> параметры аннотациями на полях и сама генерирует справку. Граница примерно
> такая: до трёх позиционных аргументов пишите руками, дальше берите библиотеку.

> **Получилось:** вы написали работающую программу целиком — она принимает
> аргументы, читает файл, считает, сортирует по двум признакам и понятно
> сообщает об ошибках с осмысленными кодами возврата. И, что важнее, устроили её
> так, что главную часть можно проверить тестами.
